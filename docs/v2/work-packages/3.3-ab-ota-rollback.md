# Work package 3.3: A/B firmware OTA and rollback

- **Status:** implementation, host fault-path tests, and reproducible
  three-target builds complete; physical interruption/rollback qualification remains.
- **Depends on:** work packages 2.4 and 2.6.
- **Scope:** a host-testable update policy, ESP-IDF A/B flash adapter, exact
  image/profile validation, local HTTP upload, rollback state, and late boot
  confirmation.

## Public behavior

The device exposes two local-network operations alongside OSCQuery and the web
asset endpoint:

| Request | Result |
| --- | --- |
| `GET /api/firmware` | update state, byte progress, and signed-image policy |
| `PUT /api/firmware` | validate, stream, activate, acknowledge, and restart |

An upload declares `X-BLIP-SHA256`, `X-BLIP-Project`, `X-BLIP-Version`,
`X-BLIP-Target`, and `X-BLIP-Profile`. The default composition accepts only
project `blip-v2`, its compile-time ESP-IDF target, and profile `minimal`. It
streams the body through the existing fixed 1,024-byte HTTP buffer; no complete
image is allocated in RAM.

Before flash erase, the service rejects an absent/oversized body or a mismatched
project, target, or profile. Before activation, it requires the exact byte count,
declared SHA-256, ESP image magic, ESP application-descriptor magic, and embedded
project/version. `esp_ota_end` then performs ESP-IDF's image, chip, checksum, and
configured signature checks. Only after all checks pass does
`esp_ota_set_boot_partition` update the redundant OTA selection record.

The endpoint is unauthenticated plain HTTP, like the existing provisioning and
web-asset endpoints. It is limited to a trusted local network or physically
controlled setup. A production profile must enable either hardware Secure Boot
or ESP-IDF's signed-app update verification and provision its verification key;
`signature_enforced` makes that platform policy visible. Release signing keys
are deliberately not committed to this repository.

The host utility derives project/version from the image and streams it with the
required metadata:

```powershell
python v2/tools/ota/blip_ota.py build/esp32/blip-v2.bin `
  --device http://192.0.2.8 --target esp32 --profile minimal
```

## Flash and rollback contract

The new 4 MiB layout is:

| Partition | Offset | Size |
| --- | ---: | ---: |
| NVS | `0x9000` | 20 KiB |
| OTA selection | `0xe000` | 8 KiB |
| PHY init | `0x10000` | 4 KiB |
| OTA slot 0 | `0x20000` | 1.5625 MiB |
| OTA slot 1 | `0x1b0000` | 1.5625 MiB |
| LittleFS | `0x340000` | 640 KiB |
| coredump | `0x3e0000` | 128 KiB |

There is no factory application. With erased OTA data, ESP-IDF selects `ota_0`;
subsequent updates alternate between the two slots. The two-sector OTA data
record is itself power-loss tolerant. The update API never selects a partially
written image, so interruption during receive or validation leaves the current
slot bootable.

Rollback support is enabled in the bootloader. On its first boot, a newly
selected image is `pending-confirmation`. BLIP confirms it only after the full
registry has started, the retained V1 migration has been confirmed, and the
diagnostics boot ledger has been committed. A crash, watchdog, or power loss
before that call causes the bootloader to reject the new slot on the next boot
and select the prior valid application.

This partition-table change cannot be installed safely as an application-only
update from 3.2. The first 3.3 installation requires a complete flash backup and
full bootloader/partition/application flash. It reduces NVS by 4 KiB, moves and
grows LittleFS, and moves/grows coredump; existing data must be exported before
the transition. Returning to 3.2 likewise requires restoring a matching
full-flash backup. These migration requirements do not alter any V1 format or
public OSC path.

The layout and state flow follow the ESP-IDF 6.0.2 [OTA API](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/ota.html)
and [signed-app verification](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/security/secure-boot-v2.html)
contracts.

## Verification

Eight focused host cases cover strict SHA-256 parsing, manifest rejection before
erase, interruption without activation, exact-length and descriptor checks,
digest rejection, chunked verified activation, and explicit one-time boot
confirmation plus failed-boot rollback. The complete fourteen-entry CTest suite, foundation validators,
resource-manifest validator, thirteen Node tests, and deterministic web-bundle
check pass.

Two independent ESP-IDF 6.0.2 build trees produced byte-identical application
images. The firmware-contract validator passed every target, including rollback
Kconfig, 4 MiB flash selection, slot capacity, toolchain flags, and target
identity. Dependency locks remained unchanged.

| Target | App image | Delta from 3.2 | Slot free | SHA-256 |

| ESP32 | 1,079,328 B | +17,008 B | 34% | `e5dda68044de03e5b3c5ff12fd87295004a0bbaf886be13cae8c283d183d620e` |
| ESP32-S3 | 1,059,344 B | +17,408 B | 35% | `18b8019540f94762d36cf355bbbf5d8be44b4d714225173c0247fdcbf0983ea6` |
| ESP32-C6 | 1,204,960 B | +19,936 B | 26% | `c91c61fdfab1ab9d1e39ff952fc573fbd1684002be60f06294370f5fbee07be8` |

The linked memory summaries report 96,901 B DRAM and 84,543 B IRAM on ESP32;
157,013 B DIRAM plus 16,384 B IRAM on S3; and 192,324 B DIRAM on C6. The update
service itself retains only bounded descriptor/hash state and reuses the 1 KiB
HTTP buffer. `esp_ota_begin` may allocate platform-owned control state during an
update; the LED render/output path is not yet present and is never entered by
the HTTP callback.

Hardware reset/power-cut records remain open. Work package 3.4 must not treat
3.3's hardware contract as stable until a real-device upload, pre-confirmation
failure rollback, and interruption sweep are recorded.
