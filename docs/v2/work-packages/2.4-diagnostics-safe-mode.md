# Work package 2.4: Diagnostics and safe mode

- **Status:** implementation, host checks, three-target builds, and physical
  reset/coredump/recovery qualification complete.
- **Depends on:** ADR-0004, work packages 1.2, 1.3, 1.5, and 2.1.
- **Scope:** structured logs, runtime levels, typed metrics, reset reporting,
  retained flash coredumps, boot-loop detection, and recovery composition.

## Runtime diagnostics contract

`EspDiagnosticsComponent` is the owner of `diagnostics.runtime`. Its descriptor
publishes the default log level, explicit `clear_safe_mode` and
`erase_coredump` actions, and 14 diagnostics covering reset/boot state, heap,
main-task stack headroom, retained coredump identity, and log loss/redaction.
The component creates no task and owns fixed storage for eight queued records,
eight per-component level overrides, and 16 metric records.

Structured records contain a monotonic sequence, microsecond timestamp, level,
component, event, and at most four typed fields. Names and strings are bounded;
non-finite numbers, invalid enum values, duplicate keys, malformed stored
records, and undersized output buffers fail closed. Secret fields are replaced
with `[redacted]` before entering the queue. A full queue drops the newest
record deterministically and increments a saturating loss counter. Formatting
uses caller-owned memory and produces one JSON object per record.

The runtime default and each bounded component override support `off`, `error`,
`warning`, `info`, `debug`, and `verbose`. Filtered, dropped, redacted, and
queue-high-water counts remain visible. `MetricRegistry` provides typed
64-bit saturating counters and signed gauges with fixed registration capacity.

## Reset and boot ledger

The boot guard owns a 32-byte, versioned RTC no-init ledger. All integers are
little-endian and CRC is IEEE CRC-32 over the record while treating its own
field as zero.

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLBH` |
| 4 | 2 | format version (`1`) |
| 6 | 2 | record size (`32`) |
| 8 | 4 | boot sequence |
| 12 | 2 | consecutive failed boots |
| 14 | 2 | failure threshold (`3`) |
| 16 | 1 | previous boot confirmed |
| 17 | 1 | safe-mode latch |
| 18 | 1 | normalized reset cause |
| 19 | 1 | safe-mode reason |
| 20 | 8 | reserved, zero |
| 28 | 4 | CRC-32 |

An unconfirmed software, panic, interrupt/task/other watchdog, or CPU-lockup
reset advances the failure streak. Three such failed boots enter safe mode on
the following boot. Cold, external, deep-sleep, brownout, USB, JTAG, eFuse,
power-glitch, SDIO, and unknown resets start a new streak. Corrupt RTC state is
discarded rather than trusted. Registry/import startup must finish before the
composition confirms a normal boot.

Safe mode registers only diagnostics and `blip.recovery`; settings, LittleFS,
legacy import, and normal bootstrap are deliberately excluded. Recovery thus
remains available when storage startup is the fault. The latch survives the
fault-reset sequence and is cleared by an explicit action or a new cold/external
streak. The recovery marker includes reason, reset cause, coredump status and
identity, heap, stack headroom, target, and ESP-IDF version.

## Coredump retention

The former final 64 KiB spare region is now the named `coredump` partition at
`0x1f0000`. ESP-IDF writes binary flash coredumps with boot validation, SHA-256
integrity, a maximum of eight tasks, a 2 KiB panic stack, and no automatic
overwrite. BLIP never erases a dump on boot. It reports absent, valid, corrupt,
or I/O-error state and computes a CRC-32 identity across the validated retained
image. Erasure is available only through the explicit diagnostics action.

The complete 2 MiB layout is 24 KiB NVS, 4 KiB PHY data, a 1 MiB factory app,
896 KiB LittleFS, and 64 KiB coredump storage.

## Memory policy

The descriptor declares a maximum feature cost of 32 KiB flash and 8 KiB RAM.
Queues, ledger storage, log encoding, coredump hashing, and metrics are bounded;
the component performs no direct heap allocation. Runtime snapshots expose
current, minimum, and largest internal-heap values plus main-task stack
high-water bytes. Per-task enumeration can be added when long-lived subsystem
tasks appear; this package has no diagnostics-owned task.

errors. Diagnostics tests cover the three-failure boot-loop threshold,
confirmation/reset behavior, corrupt ledgers, bounded queue overflow, secret
redaction, runtime levels, invalid stored records/enums, JSON overflow, typed
metrics, registry capacity, and counter saturation.

normal snapshots were:

On the C6, a qualification-only build aborted before confirmation. Three
successive panic resets entered the two-component recovery registry and emitted
`safe_reason=boot-loop`, `reset=panic`, and `coredump=valid`. The retained dump
identity was `8c028796`; ESP-IDF's offline decoder recovered the exact abort at
`app_main()` and both task stacks. Repeated panics did not overwrite the first
dump. A second qualification build exercised explicit safe-mode clearing and
restart, after which the production image reached normal readiness while still
reporting the same retained dump. Qualification macros are CMake-only and are
absent from production builds.

The S3's previously unused tail bytes were explicitly erased before assigning
the coredump partition. The ESP32 qualification board exposed pre-existing
corrupt LittleFS and an incompatible stale V1 blob; both partitions were backed
up byte-for-byte before targeted reinitialization. No qualification operation
overlapped another partition.

## Rollback

Rollback uses the previous application and partition table. The old layout
treats the final 64 KiB as spare, so a retained dump becomes dormant. Rollback
does not erase NVS, LittleFS, the RTC ledger, or the coredump bytes. Operators
must use the explicit erase action if retained crash data should be removed.
