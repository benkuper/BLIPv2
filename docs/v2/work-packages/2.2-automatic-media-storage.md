# Automatic media storage extension to work package 2.2

Status: implementation in progress; hardware/media qualification remains open.

The user's October 9 requirement applies to all bulk files: web/server assets,
scripts, playback recordings and sequence data. Consumers use logical names
and one file service. They do not select LittleFS, SD, MMC or external flash.
Board manifests declare physical media and wiring. The storage service probes
only declared hardware, prefers a successfully mounted external volume, and
otherwise uses internal LittleFS. Missing optional media must not prevent the
firmware or first-run web page from starting.

Internal files remain readable when external storage has no corresponding file.
New writes go to the preferred mounted volume. Corruption or an I/O failure is
reported rather than silently redirected to another medium. Readers and write
transactions retain their medium and generation until completion. Remounting
requires outstanding operations to close. Unknown/nonblank media is never
autoformatted.

`AutomaticFileStore` provides bounded reads, seeks, streamed uploads and small
load/save calls. Two independently checksummed generations avoid depending on
FAT overwrite-by-rename. Four readers and one writer are admitted; a generation
held by a reader cannot be overwritten. The default file limit is 16 MiB,
independent of the small working buffer. Larger playback limits require an
explicit profile decision.

The new `BLBF` format has a 40-byte little-endian header: magic (4 bytes),
format/header version (2 each), generation (8), payload size (8), logical-path
FNV-1a identity (8), flags (8; only bit 0 for a deletion tombstone). Payload follows, then a CRC-32 trailer
over header and payload. Physical generations end in `.b0` and `.b1`. A complete
durable trailer publishes a generation. Interrupted/corrupt generations cannot
supersede a valid one. The existing `BLIF` record format remains unchanged.

`AutomaticWebBackend` installs web assets through the same service under
`server/assets.bundle`. It flushes an unpublished candidate for web format/CRC
validation before publishing its trailer. The factory `web/assets.bundle` in
internal LittleFS remains a fallback; it is never compiled into the app.

The native storage component now mounts board-declared SDSPI, SDMMC or dedicated
SPI NOR media and supplies the common `storage.files` service. The legacy
`storage.files.internal` service/id remains for existing registry dependencies.
Creators Club/Tab use SPI3 for SD, with their active-low power enables. Ball C6
uses software SPI on its declared storage pins, keeping SPI2 available for
HD108 DMA on different pins. Its onboard SD-protocol storage mounted on the
connected board and accepted the checked factory bundle. Boards without media
exclude the external driver implementations. FAT mounts never autoformat.
Dedicated NOR uses LittleFS and formats only an entirely erased chip.

The HTTP file API streams uploads/downloads and deletion tombstones under
`/api/files/scripts/`, `/api/files/playback/` and `/api/files/sequences/`.
Deleting an external file does not expose an older internal fallback while
that external volume is mounted. Web files use the dedicated verified bundle
API. Manual transfers and the native update worker have exclusive admission to
avoid both resource exhaustion and competing installs on small devices.

Development hardware checkpoint: Ball external SD-protocol storage passed 51
file API checks, including script/playback/sequence byte equality, eight replacement
generations, interrupted uploads, reader cleanup, deletion versus empty files,
and persistence after reset (`build/m40-storage-ball-hil.json`). A native web
download subsequently installed into that same medium without rebooting; the
6 KiB worker retained 2,036 bytes of headroom. These focused trials do not close
the all-seven-board milestone gate. MMC/NOR providers are optional build choices;
the connected external-media boards currently declare SD SPI.

### Stored script consumer checkpoint

The production WASM worker now loads `scripts/...` logical paths through
`storage.files`. `load_file` copies its path into the existing request payload,
uses the existing module buffer, validates the pinned file generation and Wasm
module, and publishes its live controls. It remains a passive load: exports and
actions run only on explicit calls. Missing/oversized files preserve the current
module and reopen action admission. A failure after reusing its buffer leaves
the worker unloaded. The reader closes on all worker completion paths; loaded
bytes remain independent of later file replacement/deletion.

All seven release-33 production builds pass. The application increase versus
release 31 is 1,344–1,424 bytes. The worker object grows eight bytes; copied queue
slots do not grow, and the measured static RAM section totals are unchanged.
All six enumerated boards pass 13 native firmware OTA checks and 215 named-file
checks each, including 20 replacement cycles, typed guest execution, invalid
paths/modules, missing/empty/oversized files, reader reuse, deletion and actual
reset persistence. Club and Ball select SD SPI; HUZZAH32, Stick, Dial and XIAO
select internal LittleFS. Their warmed heap ranges and worker headroom are
recorded in [`2026-10-09-stored-scripts.json`](../evidence/storage/2026-10-09-stored-scripts.json).
The three chip families also pass 161 upload/runtime and 121 live-control checks
each. Host suites (33), foundation/bootstrap checks and the resource validator
pass. The latter now validates storage wiring, pin reservation, host and power
polarity rather than rejecting the existing `storage` manifest field.

Two failed harness trials remain in the evidence: a single long filename hit
LittleFS's per-component name limit (the corrected 96-byte path uses nested
components), and the initial Ball oversized-file check exceeded a two-second
completion poll during SD checksum validation (the file helper now waits up to
60 seconds). Update policies were restored after both failures. No PC network
change was made. Six devices retain confirmed release 33; the Tab is absent.
This is a consumer checkpoint, not completion of the seven-board milestone.

Remaining integration/qualification:

- Complete native hardware/media qualification; SPI NOR/MMC have no connected fixture yet.
- Qualify sustained concurrent I/O and stop while another consumer owns the filesystem.
- Connect playback/sequence consumers to stored files and define script boot/autostart policy.
- Browser file listing/management is implemented in the checkpoint below; complete its remaining qualification.
- Qualify absent/full/corrupt media, removal, interrupted transfers and reboot.
- Qualify hot-plug reprobe without invalidating readers or uploads.

### Cancellable stored-file validation

Release 34 adds a borrowed cancellation check to file opening/CRC validation.
Only cancelling consumers use the 512-byte validation chunk bound; ordinary
file and web validation retain their existing scratch sizes. No callback/context
is stored beyond the synchronous scan. Cancelled scans do not publish a reader,
fall back to an internal generation, or mutate a file. A cancelled named load
that has not reused its module buffer restores current-module action admission,
unless a later accepted replacement owns the barrier. Cancellation after buffer
reuse leaves the module unloaded.

The host test cancels at every validation check across both file generations and
immediately before reader publication, then verifies all four reader slots and
subsequent writes still work. All 33 host suites and seven target builds pass.
The release-34 addition is 608–672 application bytes versus release 33, with
unchanged static RAM sections. Individual filesystem calls and contention with
other consumers remain separate timing boundaries; cancellation cannot preempt
an SDK operation already in progress.

Club and Ball each pass **222 checks**, including an active file load cancelled
in **0.072/0.612 seconds** respectively, retained generation/edited parameters,
reopened action admission and subsequent guest execution. HUZZAH32 and M5Dial
each pass the full 215-check storage regression on the new implementation.
All four pass 13 native firmware OTA checks and retain confirmed release 34;
Stick and XIAO retain their validated release-33 images. Worker stack headroom
is 3,148/4,012/3,568/3,224 bytes for Club/Ball/HUZZAH32/Dial. Update intervals
were restored and the PC network was unchanged. Exact report, source, image,
catalog and verification hashes are in
[`2026-10-09-cancellable-stored-scripts.json`](../evidence/storage/2026-10-09-cancellable-stored-scripts.json).

The local public-JSON simulator now offers development firmware 34 and the
filesystem UI 3118 for every board profile. Publication does not turn build-only
Tab evidence into a hardware pass, or supersede the existing Stick UART burst,
strict XIAO UDP, physical media, sustained-I/O and full milestone gates.

### Browser file management

Release 35 adds bounded directory pages to the common automatic-storage API.
`GET /api/files/{scripts|playback|sequences}/[folder/]?after=<basename>` merges
external and internal entries, orders logical names and returns at most four
entries per HTTP page. A logical name can identify both a file and a directory.
Deletion tombstones stay hidden but advance the cursor, so an empty page can
still have `more: true`. Directory inventory checks metadata without reading
every payload; opening, downloading and loading a file still verifies its CRC.
Corrupt metadata is marked unreadable so the user can replace or delete it.
External I/O failures remain errors rather than silently exposing internal data.

The Advanced interface now browses all three namespaces, follows directory
pages, uploads files, downloads exact bytes, deletes files and passively loads
stored scripts. Simple mode keeps the file panel hidden. A file operation pauses
heavy configuration reads, and update admission blocks competing transfers.
Network read failures get at most two retries with fresh response buffers;
uploads, deletes and script actions are never automatically resubmitted. Short
mutation responses are fully consumed before starting another HTTP request.
Reconnecting aborts pending work and discards responses from the previous device.

All seven production builds pass. Application size increases by 4,240–4,576
bytes versus release 34, with unchanged measured static RAM sections. XIAO's
application is 1,626,816 bytes, leaving 11,584 bytes in its current OTA slot.
The complete 12-asset UI is 33,044 bytes in the filesystem bundle, separate from
the application; all seven factory filesystem images contain source version
0.3.9/code 3009. The local public update simulator offers firmware 35 and the
same UI as development release 3122.

All **33 host suites** and **41 browser unit tests** pass. Each of the six
enumerated boards passes **265 directory/file API checks** and **22 real Edge
browser checks**, including all namespaces, pagination, exact 32 KiB playback
downloads, passive script loading, deletion, a 390-pixel layout and paused
configuration reads during transfers. Club and Ball use their SD SPI volumes;
HUZZAH32, Stick, Dial and XIAO use internal LittleFS. All six pass 13 native
firmware update checks and the initial 10-check UI update trial. Final source
and status checks verify firmware 35 is confirmed and UI 3122 is installed on
all six. Some final UI trials timed out at the PC's HTTP verification step;
their original failed reports remain recorded alongside the successful follow-up
checks rather than being reclassified as passes.

HTTP task stack headroom after the final trials ranges from 2,424 to 3,200
bytes. Ball's captured browser run records HTTP send timeouts and a socket reset;
bounded read retries still returned the complete expected file. Earlier network
changes, truncated responses and startup module failures remain in the evidence.
The browser harness records up to two startup page reloads before exercising
controls; this does not establish uninterrupted bootstrap or sustained operation.
Ball's historical minimum free internal heap is 1,684 bytes, so sustained memory
and radio coexistence qualification remains open.

Owned fixture payloads were reclaimed, passive modules unloaded and update
policies restored. Empty fixture directories remain because directory deletion
is not yet exposed. No PC network change was made. Six boards retain the validated
firmware and UI; Creators Tab is still absent. The seven-board milestone, physical
MMC/NOR and hot-plug trials, sustained concurrent I/O, playback/sequence consumers
