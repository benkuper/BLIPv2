# Work package 3.2: Filesystem-managed web asset bundles

- **Status:** implementation, automated recovery checks, and reproducible
  three-target builds complete.
- **Depends on:** work packages 2.2 and 3.1.
- **Scope:** a deterministic web bundle, bounded LittleFS bundle manager,
  factory recovery image, on-device static serving, and an independently
  updatable local-network endpoint.

## Public behavior

The work package 3.1 shell is now served directly by the device. Browser
navigation to `GET /` with `Accept: text/html` returns `/index.html`; the other
bundle paths are served by their exact names. The existing OSCQuery contract is
unchanged: `GET /`, `GET /?HOST_INFO`, and the configuration queries without an
HTML navigation request still return registry JSON, and the root WebSocket still
carries OSC.

The management surface is deliberately small:

| Request | Result |
| --- | --- |
| `GET /api/web-assets` | active format, bundle version, asset count, byte size, and CRC |
| `PUT /api/web-assets` | stage, verify, and atomically activate one complete bundle |

An upload must declare a body between 48 bytes and 256 KiB. The server receives
it through a fixed 1,024-byte buffer, durably closes the staging file, validates
the complete bundle, and then renames it over the active file. A malformed,
truncated, oversized, or CRC-invalid candidate is deleted without changing the
active bundle. A reset during upload may leave a staging file, which the next
boot removes before validating the active bundle. If a rename reports failure
after taking effect, the manager reloads the active file and accepts it only
when its CRC matches the verified candidate.

The endpoint is unauthenticated plain HTTP and has no cross-origin update
permission. It is intended only for a trusted local network or a physically
controlled provisioning workflow. Internet exposure requires a future
authenticated gateway. This package does not publish the device UI to a public
hosting service; the deployment target is the device's LittleFS partition.

## Bundle format

The checked-in factory file uses little-endian `BLWB` format version 1. It is
12,403 bytes, contains seven gzip-compressed source assets, has semantic bundle
version 1000 (`0.1.0`), and has SHA-256
`d1da478cbae6e4a72fb3d02ff4b854e4a0815258b6dbf49892123143983b6c4d`.

The 48-byte header is:

| Offset | Field |
| ---: | --- |
| 0 | `BLWB` magic (4 bytes) |
| 4 | format version (`u16`) |
| 6 | header size (`u16`) |
| 8 | independently incremented bundle version (`u32`) |
| 12 | entry count and zero flags (`u16`, `u16`) |
| 16 | manifest, payload, and total byte sizes (three `u32`) |
| 28 | bundle, manifest, and payload CRC-32 values (three `u32`) |
| 40 | zero-reserved bytes (8 bytes) |

The bundle CRC covers the complete file with its own field zeroed. Every
96-byte manifest entry declares a path length, content type, content encoding,
cache policy, contiguous payload offset, stored/original size, stored-data CRC,
and a zero-padded 64-byte path. Entries must be strictly sorted and unique,
paths are bounded to 63 ASCII bytes, offsets have no gaps, all reserved fields
are zero, and `/index.html` is mandatory. Validation checks the header,
manifest, payload, and every individual asset using a fixed 512-byte scratch
buffer.

The deterministic packer fixes gzip metadata, ordering, compression level,
reserved bytes, and version encoding. CI fails if the committed factory bundle
does not reproduce the current web source:

```powershell
npm run build --prefix v2/web
```

To generate a candidate and install it on a trusted device:

```powershell
python v2/tools/web/pack_web_assets.py --source v2/web `
  --output build/web/assets.bundle --upload http://192.0.2.8
```

## Recovery and factory behavior

LittleFS stores the active file at `web/assets.bundle` and the staging file at
`web/assets.upload`. On every boot, the manager removes stale staging data and
verifies the active bundle. A valid independently installed bundle is retained
regardless of the firmware's embedded factory version. A missing, corrupt,
incompatible, or unverifiable
active file is replaced with the firmware-embedded factory bundle. Other I/O
errors fail storage startup instead of silently formatting or discarding data.

The storage descriptor now publishes `storage.web_assets` and read-only bundle
version/count/size parameters. The readiness marker reports the same values.
Static serving adds `nosniff`, a restrictive HTML content-security policy,
explicit cache policy, gzip encoding, and CRC/size ETags. Non-fingerprinted
assets revalidate; the HTML entry is never stored.

## Verification

Six focused host tests exercise factory installation and streaming, corrupt
candidate rejection, interruption before completion, successful replacement,
boot cleanup and corrupt-active recovery, rename failures before and after
mutation, scratch/bundle limits, and bounded reads. The complete thirteen-entry
CTest suite and thirteen Node tests pass.
The Python packer also verifies that decompression exactly reproduces every
source asset.

Two independent ESP-IDF 6.0.2 build trees produced byte-identical application
images. All targets passed the firmware-contract validator and retain at least
25% of the 1.5 MiB app partition.

| Target | App image | Delta from 3.1 | SHA-256 |
| --- | ---: | ---: | --- |
| ESP32 | 1,062,320 B | +22,688 B | `be16de864ea167dd8e21dd1bbd3866304d62a7f63a8dc66877a5266499c6655e` |
| ESP32-S3 | 1,041,936 B | +22,688 B | `597d1024874d6c5dda5b071a470b3fd59652ef4eeeb1e2140285a74c6f25d8c3` |
| ESP32-C6 | 1,185,024 B | +23,584 B | `65c4cb14d6bc70d16695b02642ea20991e98acb014cac531dfdc9e821a4b22ae` |

The delta includes the 12,403-byte embedded recovery bundle, bundle validation
and streaming code, HTTP routes, and metadata. Runtime buffers and tables have
fixed capacities; upload and serving perform no whole-bundle heap allocation.
Physical browser/provisioning repetitions and randomized hardware power cuts
remain part of Gate B rather than being claimed by this work package.

## Rollback

Rolling firmware back to 3.1 removes static serving and the bundle-management
endpoint but does not change the partition table. The active and staging files
remain ordinary LittleFS data and may be removed later. Rolling back to an
earlier 3.2 firmware keeps any valid format-1 active bundle, so firmware rollback
does not silently downgrade the UI. A future incompatible bundle format must
ship a compatible factory image or an explicit migration.
