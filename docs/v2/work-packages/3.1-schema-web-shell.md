# Work package 3.1: Schema-driven web shell

- **Status:** implementation, automated web checks, host regression tests, and
  reproducible three-target builds complete.
- **Depends on:** ADR-0001, ADR-0004, work packages 1.3 and 2.7.
- **Scope:** a dependency-free browser shell generated from the live registry's
  OSCQuery representation, plus additive registry-derived UI annotations.

## Public behavior

The shell fetches `/?HOST_INFO` and either `/?config=1` or `/?config=0` from a
device. It renders every component container with direct controls and never
contains a handwritten component ID, OSC path, or component panel. Adding the
synthetic motion component in the model test therefore creates a complete new
panel and numeric editor without a web-source change.

Controls use the existing root WebSocket and bounded binary OSC messages:

| Registry control | Generated editor |
| --- | --- |
| boolean parameter | checkbox |
| bounded integer or number | numeric input with minimum, maximum, and step |
| enumerated parameter | select |
| readable string | text input |
| write-only string | password input with no reflected value |
| read-only parameter or event | live output |
| action | button plus typed argument fields |

The interface includes connection state, explicit reconnect, configuration
filtering, control search, responsive layouts, reduced-motion behavior, and
keyboard-accessible native forms. It uses only text nodes for device-provided
labels and values; registry strings are never interpreted as HTML.

When hosted from the device, the shell uses its own origin. During 3.1 local
development, `?device=http://<device>` selects a separate target. Embedding,
compression, signing, and independent updating of these source assets are
deliberately deferred to work package 3.2.

## Registry and OSCQuery ownership

OSCQuery remains the wire representation of the registry rather than a second
web schema. Work package 3.1 adds namespaced, additive annotations:

- `BLIP_KIND` distinguishes roots, namespaces, components, parameters, actions,
  and events;
- component containers include ID, schema version, and disable policy;
- parameters include persisted/readable/writable flags plus optional step and
  unit values;
- actions and events include typed `BLIP_FIELDS` with stable field IDs and
  required flags.

Legacy OSCQuery clients may ignore these properties. All V1 paths, standard
OSCQuery fields, values, ranges, access values, and OSC behavior are unchanged.
The host-info extension table advertises `BLIP_KIND` and `BLIP_FIELDS` support.

## Bounds and security

The browser codec mirrors the firmware limits: one 1,024-byte packet, a
128-byte address, 256-byte strings, and eight arguments. It validates UTF-8
decoding, four-byte alignment and zero padding, finite numbers, fixed-width
integer ranges, exact packet length, and supported tags. Schema responses are
limited to 16 KiB for host info and 256 KiB for the tree; traversal is limited
to 16 levels and duplicate/invalid paths fail closed.

The shell stores neither device URLs nor parameter values. Write-only controls
are masked and never populated from the tree. As in work package 2.7, HTTP and
WebSocket control is unauthenticated and unencrypted on plain HTTP, so this
surface is restricted to a trusted local network.

## Verification

Thirteen Node tests cover model generation, a component-addition acceptance case,
legacy-field fallback, typed input coercion, filtering, duplicate/malformed
schema rejection, bounded OSC scalar and compatibility-type round trips,
zero-argument actions, corrupt packets, target URL handling, response bounds,
and offline-send rejection. The complete twelve-entry C++ CTest suite also
passes, including expanded OSCQuery assertions for every new annotation.

Two independent ESP-IDF 6.0.2 build trees produced byte-identical application
images. All six builds passed the firmware-contract validator and the dependency
locks were unchanged. Browser source is not yet embedded and therefore consumes
zero device flash/RAM; the table delta is the additive OSCQuery annotation writer.

The smallest target retains 26% of the 1.5 MiB application partition. The
annotation writer adds no component state, task, queue, heap allocation, or
static RAM. The unminified production web source is 37,746 bytes on the host and
is intentionally excluded from these firmware measurements.

## Rollback

This package changes no partition table, persisted record, or OSC path. Rolling
back to 2.7 removes the local shell and the additive `BLIP_*` JSON properties;
existing OSC/OSCQuery clients continue to work. No data migration or downgrade
step is required.
