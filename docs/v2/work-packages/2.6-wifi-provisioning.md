# Work package 2.6: Wi-Fi station/AP management and provisioning

- **Status:** implementation, host checks, reproducible three-target builds, serial
  qualification, and SoftAP HTTP qualification complete.
- **Depends on:** ADR-0001, ADR-0004, ADR-0006, work packages 1.3, 1.4, 2.1, 2.3,
  and 2.5.
- **Scope:** bounded Wi-Fi configuration, ESP-IDF station/AP lifecycle, serial and
  SoftAP provisioning, V1 Wi-Fi settings normalization, and radio-resource ownership.

## Public behavior

`blip.transport.wifi` provides `transport.wifi` and requests the multiplexed
`radio0` resource. Its descriptor exposes enabled state, station/AP mode, SSID,
static IPv4 fields, channel scanning, transmit-power profile, protocol profile,
preferred channel, antenna selection, normalized signal, connection state, and
worker stack headroom.
The password parameter is write-only: registry reads fail with the structured
`control.invalid_state` / `write-only` error, and descriptor JSON identifies the
access mode without emitting a value.

The `provision(ssid, password)` action is available through the common serial
control envelope. A blank device starts an open `BLIP-XXXXXX` AP at `192.168.4.1`
and serves a bounded HTML form at `/`; `POST /provision` accepts only the `ssid`
and `password` URL-encoded fields. Bodies are limited to 384 bytes, SSIDs to 32
bytes, WPA passphrases to printable 8-63 byte values, and open networks use an
empty password. Unknown, duplicate, malformed, oversized, invalid-UTF-8, and
partially specified inputs fail closed.

Portal submissions return `202 Accepted` only after the settings record is durable.
The worker waits one second before applying that saved radio configuration so the
HTTP response can leave the AP. Once started, the bounded HTTP server task remains
allocated until component shutdown; only the AP radio is removed after a successful
station connection. This avoids stopping a server from one of its own callbacks and
keeps provisioning reachable throughout association. Serial changes instead complete
radio application and NVS persistence before their success response.

The state values are:

| Value | State |
| ---: | --- |
| 0 | off |
| 1 | connecting |
| 2 | connected |
| 3 | connection error with fallback AP |
| 4 | disabled |
| 5 | hotspot/provisioning |

Station retries use bounded exponential delays from 500 ms to 5 seconds. A
station-only configuration retains or starts the setup AP after 20 seconds without
a connection. Station+AP mode retains the hotspot across disconnects. DHCP is the
default; manual IP and gateway must be supplied together. Wi-Fi 6 (`ax`) is accepted
only on targets whose ESP-IDF capability declares HE support.

The persisted antenna values are `0` board-default, `1` onboard, and `2`
external. Explicit onboard/external selection fails with `resource_unavailable`
unless the board build declares an RF switch. The Seeed Studio XIAO ESP32C6
build option drives GPIO3 low to enable switch control and GPIO14 low/high for
the onboard ceramic/U.FL path, matching Seeed's
[RF-switch contract](https://wiki.seeedstudio.com/xiao_esp32c6_getting_started/#hardware-overview).

## Settings and compatibility

Native settings use a bounded `BLWF` version-2 record. Its 24-byte little-endian
header contains version/header size, CRC-32, booleans/enums, four string lengths,
antenna selection, and one zero reserved byte; the exact-length payload concatenates SSID, password,
manual IP, and gateway. The maximum encoded record is 149 bytes inside a 192-byte
caller-owned buffer. Prefix truncation, CRC damage, invalid enums, bad reserved
bytes, inconsistent lengths, invalid addresses, and unsafe passphrases are rejected.
Version-1 native records remain readable and migrate to board-default antenna
selection; their next settings write emits version 2.

The V1 `/wifi` import maps `enabled`, `mode`, `ssid`, `pass`, `manualIP`,
`manualGateway`, `channelScanMode`, `txPower`, `wifiProtocol`, and `channel` into the
native record. Import is one-way through the existing journaled coordinator; the
source V1 blob is retained. Passwords necessarily remain inside persisted settings,
but are never exposed by control reads, descriptors, logs, HTTP responses, or
diagnostics. This package does not add or change OSC paths; the 2.7 compatibility
adapter will map the preserved V1 Wi-Fi hierarchy to this descriptor.

## Memory, tasks, and partition migration

The component object is 8,304 bytes on ESP32, ESP32-S3, and ESP32-C6, below its
10 KiB static-RAM declaration. It owns a static 6 KiB priority-4 worker stack; the
ESP-IDF HTTP server uses a bounded 4 KiB stack after first portal start. Configuration
and retry counters saturate. NVS writes and radio reconfiguration run only on the
worker, protecting the priority-5 serial task's 4 KiB stack. The worst observed
worker high-water headroom after serial and HTTP provisioning was 2,464 bytes.

Linking ESP-IDF Wi-Fi, netif, lwIP, and HTTP support no longer fits the former 1 MiB
factory partition on ESP32-C6. The 2 MiB compatibility layout is therefore now:

| Region | Offset | Size |
| --- | ---: | ---: |
| NVS | `0x9000` | 24 KiB |
| PHY init | `0xf000` | 4 KiB |
| factory app | `0x10000` | 1.5 MiB |
| LittleFS storage | `0x190000` | 384 KiB |
| coredump | `0x1f0000` | 64 KiB |

This is a partition-table migration. A device using the earlier V2 table must back up
or export LittleFS before flashing the new table because the app now occupies its
former `0x110000..0x18ffff` range and only `0x190000..0x1effff` remains storage.

## Verification

Eleven host CTest entries pass with warnings as errors, exceptions disabled, and RTTI
disabled. Six Wi-Fi cases cover native round trip and every corrupt prefix, unsafe
credentials and addresses, V1 import, strict form parsing, retry/fallback/disable
transitions, and station+AP disconnect recovery. Foundation, bootstrap, resource
manifest, and pinned clang-format 18.1.8 checks also pass.

## Hardware evidence

COM6 identified an ESP32-PICO-D4 revision 1 with MAC `50:02:91:9c:36:ac` and
4 MiB physical flash. Before changing its partition table, the complete flash was
backed up as `build/m26-com6-before-full-4mb.bin` (4,194,304 bytes, SHA-256
`cd3517473707d59c3d915b52a3e16213cadce80d9ffb2b4371958fb7acb51a08`).
Only the new 384 KiB storage range was then erased; the backup makes that operation
recoverable.

The production image booted blank as `BLIP-9C36AC`; both a raw HTTP GET and a browser
render reached the setup form at `192.168.4.1`. A real form submission returned HTTP
202, persisted synthetic credentials, and began station association without reflashing.
Serial provisioning independently persisted synthetic credentials, immediately read
back the new SSID, reached state 3 after the 20-second failure timeout, and kept the AP
reachable. Password readback was rejected. An early synchronous-NVS prototype exposed
a serial-task stack overflow; the retained dump led to the dedicated worker design and
was explicitly erased after the fixed path passed.

The final cold boot reported `coredump=absent`, `wifi_state=5`, free heap 164,048 bytes,
largest block 110,592 bytes, and main-task stack headroom 4,896 bytes. Synthetic serial
and HTTP credentials were removed, the workstation's temporary AP profile was deleted,
and the device was left blank in hotspot state.

## Rollback

Application-only rollback is safe for firmware already using this 1.5 MiB layout. To
return to the earlier V2 or V1 partition table, restore a matching full-flash backup or
flash the old table/application and restore the old LittleFS bytes; flashing only the
old application would exceed its former 1 MiB slot assumptions. The COM6 image above
restores the exact pre-migration bootloader, partition table, application, NVS,
LittleFS, and tail data.
