# Work package 2.2: Atomic file storage

- **Status:** implementation, host fault injection, three-target builds, and
  physical mount/reboot checks complete. Gate A rows `A-04` through `A-06`
  remain open and are not claimed by this package.
- **Depends on:** ADR-0005 and work package 2.1.
- **Scope:** the common bounded file store, internal LittleFS service, optional
  mounted-SD service, V2 partition table, dependency locks, and host tests.

## Compatibility disposition

- **Preserved:** V1 source, NVS keys, public OSC paths, and file formats are
  unchanged. An unrecognized nonblank storage partition is never formatted
  automatically.
- **Changed for V2:** the firmware has a named 896 KiB `storage` partition and
  exposes `storage.files.internal`. Stored records carry a format version,
  logical path, generation, explicit lengths, and CRC-32.
- **Optional:** `SdFileStorageComponent` wraps a board/profile-provided mount
  service and exposes `storage.files.sd`; it is not enabled by a generic target
  and assigns no pins or buses.
- **Removed:** no V1 behavior or data is removed by this package.

## Service contract

`AtomicFileStore` operates on an injected `FileBackend` and uses caller-owned
scratch memory. It allocates no heap, creates no task, and accepts relative
logical paths of at most 96 bytes from a restricted character set. Absolute
paths and traversal are rejected. Input/output buffers may not overlap the
scratch buffer.

The production LittleFS component owns 4,096 scratch bytes, so its maximum
payload is `4096 - 32 - logical_path_length` bytes. This bounded record API is
for settings, manifests, and control-state files. Bulk/streaming asset transfer
is deliberately deferred to work package 3.2 and will use a streaming writer,
not a larger permanent scratch allocation.

The common backend makes file data durable with `fflush`, `fsync`, and close.
LittleFS uses verified temporary-file replacement. Removable filesystems use
two complete generations plus an integrity-checked pointer, because their
rename/power-loss guarantees vary. Parent directories are created within the
configured mount root. The service must run in the storage/maintenance class.

## Persisted byte formats

All integers are little-endian. CRC is standard IEEE CRC-32 over the entire
record while treating its own four-byte field as zero.

### File record `BLIF`, format 1

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLIF` |
| 4 | 2 | record format version (`1`) |
| 6 | 2 | fixed header size (`32`) |
| 8 | 8 | monotonically increasing generation |
| 16 | 2 | logical-path byte length |
| 18 | 2 | flags, currently zero |
| 20 | 4 | payload byte length |
| 24 | 4 | reserved, zero |
| 28 | 4 | CRC-32 |
| 32 | variable | UTF-8 logical path followed by opaque payload |

### Slot pointer `BLFP`, format 1

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLFP` |
| 4 | 2 | record format version (`1`) |
| 6 | 2 | record size (`32`) |
| 8 | 8 | full 64-bit FNV-1a logical-path hash |
| 16 | 8 | committed generation |
| 24 | 1 | selected slot (`0` = A, `1` = B) |
| 25 | 3 | reserved, zero |
| 28 | 4 | CRC-32 |

## Commit and recovery rules

For LittleFS, save writes and syncs `<path>.tmp`, reads back and verifies the
complete record, atomically renames it over `<path>`, then verifies the committed
record. A reset before rename retains the old record; a reset after rename sees
the new record.

For SD, save inspects `<path>.a`, `<path>.b`, and `<path>.ptr`; writes and verifies
the inactive generation; then writes and verifies the pointer. A valid pointer
wins. If the pointer is missing, torn, or stale, the highest complete valid slot
is selected deterministically. A corrupt selected slot falls back to the other
valid generation. No valid record yields a typed `corrupt_data` error rather
than silently returning defaults.

LittleFS mount never uses `format_if_mount_failed`. The component scans the
entire named partition after a failed mount and formats only if every byte is
erased (`0xff`). Nonblank unknown or corrupt data fails startup so a later
explicit migration/recovery path can preserve it.

## Dependency and partition policy

The official ESP-IDF component registry dependency `joltwallet/littlefs` is
exactly pinned to `1.21.1`; all target locks contain component hash
`29eff7921c4e8bce021aeb7fff2723bfcafed661756de700646ea0f6223c2a32`.
That release supports ESP-IDF 5.0 and newer, including the pinned 6.0.2 toolchain.
Generated managed-component source remains ignored; the manifest and lock files
are the reproducible inputs.

The 2 MiB-safe partition layout contains 24 KiB NVS, 4 KiB PHY data, a 1 MiB
factory application, and an 896 KiB LittleFS partition. Work package 2.4 assigns
the final 64 KiB, which was spare when this package landed, to retained
coredumps. A larger detected chip does not change these offsets.

## Verification

Five file-storage host tests cover both policies, round trips, every
before/after mutation interruption boundary, pointer corruption, selected-slot
corruption, the format-1 golden structure, CRC rejection, traversal rejection,
and scratch/output capacity. All five CTest executables pass (33 logical tests
including earlier packages), with exceptions and RTTI disabled and warnings as
errors.

ESP-IDF 6.0.2 target builds and firmware-contract checks pass:

Two independent clean build trees per target produced byte-identical
application images with the hashes above.

The explained cost increase is the 4 KiB service scratch plus LittleFS, VFS,
stdio, and partition support. `libjoltwallet__littlefs` contributes 25,768 B,
26,419 B, and 31,556 B respectively; BLIP storage contributes 4,810 B, 4,810 B,
and 5,368 B. The component creates no task and reserves no task stack.

On the connected Adafruit HUZZAH32 Feather, M5 Dial/StampS3, and XIAO ESP32-C6,
the new partition table flashed successfully. Nonblank legacy bytes on the S3
and C6 were refused rather than erased. For the destructive qualification step,
only `0x110000..0x1effff` was explicitly erased on each test board; NVS was left
intact. All three devices then formatted blank media, mounted, and reached the
full readiness marker. A second reset mounted the retained filesystem and
reached readiness in 308 ms, 277 ms, and 245 ms respectively. This is physical
mount/reboot evidence, not a claim for Gate B's later 1,000 randomized power-cut
test.

## Rollback and migration

Rollback is the prior firmware and partition-table artifact. The source tree
contains no V1 edits. V2 will not erase unknown nonblank storage; an operator
must explicitly provision blank media or a later importer must recognize it.
Removing the service leaves its partition bytes dormant. SD slot files use
suffixes `.a`, `.b`, and `.ptr` and can be removed together by an explicit
maintenance action.
