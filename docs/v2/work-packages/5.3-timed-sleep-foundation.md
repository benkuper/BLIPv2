# 5.3 Timed sleep foundation

The USB-powered Adafruit HUZZAH32 profile exposes `blip.power.sleep` over the
V2 control registry. Its `light_sleep(duration_ms)` and
`deep_sleep(duration_ms)` actions accept 1000 to 30000 ms and arm an ESP-IDF
timer wake. Light sleep resumes the running firmware; deep sleep starts a fresh
boot. Both actions require the Wi-Fi radio and pixel output to be disabled. A
worker waits for the serial acknowledgement and UART drain before entering
sleep, then checks those preconditions again. The registry reports light-sleep
state, completed cycles, wake cause bitmask, ESP-IDF error, and measured
interval. After deep sleep, it reports the boot wake cause and reset kind.
Runtime diagnostics also expose boot sequence and reset cause as registry
parameters so a test can prove that a new boot occurred.

`v2/tools/control/blip_sleep_hil.py` saves both `enabled` settings, disables
them, requests sleep over serial, waits for the timer, checks the wake result,
and restores the saved settings. It checks a new boot sequence and deep-sleep
reset cause for the deep path. Light-sleep evidence is recorded in
`docs/v2/evidence/board-bringup/2026-10-01-huzzah32-timed-sleep.json`; deep-sleep
and repeated-boot evidence is in `2026-10-01-huzzah32-deep-sleep.json` in the same
directory.

This is a controlled qualification path. The other five profiles have no sleep
action yet. Creators Ball V2, Creators Tab, and M5Dial have board power latches;
their hold and wake behavior must be verified before deep sleep is enabled.
The Ball's GPIO19 button is outside the ESP32-C6 RTC deep-sleep GPIO set.
The ESP-IDF [sleep API](https://docs.espressif.com/projects/esp-idf/en/v6.0/esp32/api-reference/system/sleep_modes.html)
provides the timer wake and sleep calls used here. The 80–160 MHz scaling and
pixel-frame lock are described in `5.3-pm-dfs.md`. Automatic idle sleep,
other-board sleep coordination, locks for additional timing-sensitive work,
and measured idle/sleep current on each board remain open for milestone 5.3.
