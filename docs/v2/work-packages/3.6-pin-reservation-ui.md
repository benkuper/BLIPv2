# Work package 3.6: Pin reservation inspector and conflict-safe editor

- **Status:** implemented and host/AP-qualified on 2026-08-15; interactive
  browser-dialog and multi-component physical reassignment remain Gate B fixture work.
- **Depends on:** work packages 1.3, 1.4, 2.1, and 3.1.
- **Compatibility:** additive V2 behavior. V1 has no equivalent reservation
  feedback or transactional reassignment contract.
- **Scope:** expose the board pin inventory and the resource broker's effective
  reservations to the schema-driven web UI, then use that data for every
  pin-valued parameter and for one board-wide reservation view.

## Authoritative model

The resource broker remains the only authority for availability. The web UI
must not infer conflicts from parameter values or maintain a second allocation
table. The device publishes a versioned, bounded snapshot containing every
board-declared pin, including pins that cannot be selected, with:

- stable pin ID, physical/board label, GPIO number where applicable, and
  electrical/capability metadata;
- effective state: free, exclusively claimed, compatibly shared, reserved, or
  unavailable for the requesting parameter;
- every current owner as a stable `component:parameter` path, its claim mode,
  and its human-readable role;
- a machine-readable reason for an unavailable or incompatible state;
- bus/controller membership and compatible co-owners rather than one lossy
  "in use" string; and
- a monotonically changing allocation revision used to reject stale edits.

System reservations and board-critical roles, including pins required for
flash, PSRAM, boot, or an enabled non-reconfigurable board function, are visible
with their reason but are never offered as assignable or reclaimable. The board
manifest, not a hard-coded web list, identifies these roles.

## Pin parameter behavior

Focusing or opening any pin selector shows all board-declared pins. Each entry
shows its current role and one of these outcomes:

| State for this parameter | UI behavior |
| --- | --- |
| free and compatible | selectable |
| already selected by this parameter | selected and identified |
| compatible shared claim | selectable and labelled with every co-owner |
| owned by another configurable `component:parameter` | selectable only through an explicit reassignment flow |
| system/critical reserved | disabled, with the reservation reason |
| electrically or functionally incompatible | disabled, with the failed capability or constraint |

Choosing a pin held exclusively by another configurable parameter never steals
it silently. A confirmation names both full parameter paths and offers only the
operations that validate:

1. **Swap assignments** exchanges the two pin values and leases when each pin
   satisfies the other parameter's constraints.
2. **Unassign previous and move** clears the previous owner's optional pin
   parameter, releases its lease, and assigns the pin to the requesting
   parameter.

The second operation is unavailable when the previous setting is required or
the component cannot safely release it. If either affected component requires a
restart, the UI labels the operation as staged/reboot-required and lists every
affected component before confirmation.

Reassignment is one broker-backed settings transaction: validate the complete
proposed state, stop or stage affected components as declared, update settings
and leases, and either commit everything or restore the previous state. The
request includes the snapshot allocation revision; a stale revision fails with
fresh owner details instead of overwriting a newer choice. Persistence failure,
lease failure, component restart failure, disconnect, or timeout must not leave
an exclusive pin assigned twice or only half of a swap committed.

## Board-wide pin and reservation view

The web application includes a dedicated view of the complete board inventory,
not only pins referenced by the currently visible component. It supports
search/filtering and shows pin label/number, capabilities, electrical mode,
availability, all owners and `component:parameter` paths, bus membership, and
the exact reserved/conflict reason. Multiple legal owners are displayed
individually. Selecting an owner navigates to its generated component control.

The view updates after edits and broker lifecycle changes. It must distinguish
configured intent from the effective live lease when an operation is staged for
reboot, so a user is never shown a future assignment as if it were already
active.

## Shared buses, especially I2C

I2C SDA/SCL are a bus/controller assignment. Sensor and peripheral components
join that bus; they do not appear as mutually conflicting exclusive owners of
the same two pins. The inspector shows the bus, its SDA/SCL pins, electrical and
speed constraints, and every member component.

Compatible I2C members may coexist. An incompatible controller, pin pair,
pull-up/electrical requirement, or duplicate in-use device address is reported
as the actual constraint instead of a generic pin conflict. Changing SDA or SCL
is a bus-level transaction that validates and lists all affected members; the UI
does not offer a misleading single-device pin swap. A component that can use an
existing compatible bus should select or create a bus assignment and its device
address, rather than reserve duplicate SDA/SCL parameters.

The schema supports the same grouped-resource representation for SPI, UART, and
future shared resources, but I2C behavior and address-conflict tests are required
for this work package.

## Acceptance and tests

- Every board-declared pin appears in both the selector model and the complete
  reservation view, including system/critical and incompatible pins.
- Exclusive, reserved, shared, incompatible, required-setting, and
  reboot-required states have distinct machine-readable values and visible
  explanations; color is not the only indicator.
- Free assignment, valid swap, and valid unassign-and-move succeed and persist;
  invalid or stale operations leave settings, leases, and running components
  unchanged.
- A simulated failure at each transaction stage proves rollback and confirms
  that no snapshot ever contains two incompatible exclusive owners.
- Two compatible I2C devices share one SDA/SCL bus without a false pin conflict;
  duplicate addresses and incompatible bus constraints fail with both claimants
  identified.
- Changing an I2C pin identifies and validates every bus member, and cannot be
  submitted as an isolated device-pin edit.
- Browser tests cover keyboard operation, disabled-reason text, confirmation
  wording, navigation between the board view and component controls, live
  refresh, stale-revision recovery, and configured-versus-effective state.

## Rollback

Removing the UI and its additive resource-schema fields restores the generic
3.1 controls. It must not modify existing assignments. Any persisted allocation
format introduced by implementation is versioned and remains readable by the
firmware even when the specialized web view is absent.

## Implementation record

- Versioned JSON manifests and a fixed-capacity compiled inventory cover the
  HUZZAH32, M5Dial, and XIAO ESP32-C6 reference boards. The XIAO reference build
  uses its onboard antenna and reserves GPIO3/GPIO14 for the RF switch.
- `GET /api/resources` publishes the board, allocation revision, all pins,
  capabilities, electrical constraints, exact reasons, buses, configured/effective
  owners, roles, ownership modes, member keys, and restart/optional flags.
- Registry metadata marks pin-valued controls. The web shell derives selectors
  only from that metadata, shows all pins and reasons, and includes the searchable
  board-wide inspector and owner navigation.
- `POST /api/resources/reassign` validates the expected revision and both
  component descriptors before executing a broker transaction. No ordinary
  parameter write can steal a held GPIO; the RMT strip acquires and retains its
  GPIO lease across persistence and rolls back a failed change.
- Host tests cover stale revisions, swap, required-owner rejection, failure at
  each transaction stage, shared I2C members and duplicate addresses. Browser
  tests cover normalization, complete outcomes, conflict wording inputs, explicit
  operation construction, filtering, and malformed snapshots.
- Evidence: `docs/v2/evidence/pin-reservations/2026-08-15-pin-reservations.json`.
