# 5.5 BLE control transport foundation

The shared framing and dispatch layer now has an opt-in NimBLE GATT service. The C6 hardware link and live suspension have been tested. Original ESP32 memory qualification, ESP32-S3 hardware testing, and the six-board BLE acceptance gate remain open.

The existing BLIP control envelope can now be handled without serial COBS framing. The serial endpoint uses this shared handler, so BLE can submit the same binary request and receive the same binary response, including structured control errors and request IDs. A HUZZAH32 app build was flashed and its serial control probe passed after the refactor.

BLE GATT values use a four-byte header: flags (`START=1`, `END=2`), an 8-bit frame ID, and a little-endian 16-bit byte offset. The remaining bytes carry a slice of one raw BLIP envelope. The bounded assembler rejects missing, duplicate, reordered, oversized, and incorrectly flagged slices. A new `START` can recover from an abandoned partial request. Response slices advance only after an acknowledgement, allowing the eventual GATT service to use indications. Host tests round-trip the maximum envelope with 20-byte GATT values (default ATT MTU 23), then exercise ordering and bounds failures.

`BLIP_ENABLE_BLE` defaults to off. The ordinary firmware build excludes the BLE GATT source and NimBLE configuration. Opting in selects `sdkconfig.ble.defaults`, which enables one peripheral connection and removes unused central, observer, and broadcaster roles. It also defaults Art-Net and DDP off to leave app space; they can still be requested explicitly. `blip.transport.ble.enabled` is persisted and defaults to false. Disabling it waits for any response indication to be acknowledged, then stops advertising and deinitializes NimBLE; serial control remains available.

The service UUID is `6a6a83c0-64cf-43f4-8a3a-8bd713d24300`. Its RX characteristic at suffix `4301` accepts acknowledged writes, and its TX characteristic at suffix `4302` sends indications. Control dispatch runs in a separate worker task, outside the NimBLE host callback. The service exposes active, advertising, connected, subscribed, received-request, acknowledged-response, and rejected-chunk readbacks. `v2/tools/control/blip_ble_control.py` scans, connects, fragments requests to the negotiated MTU, reassembles indications, and decodes structured control responses.

On the XIAO ESP32-C6, an opt-in build with Art-Net, DDP, and E1.31 excluded flashed and answered BLE get/set requests. A BLE write changed `blip.bootstrap.probe_value`, and serial readback saw the same value. The device suspended NimBLE after a BLE write of `enabled=false`, disappeared from scanning, re-enabled by serial control, and restored the saved enabled state after reset. The selected image is `0x18dfb0` bytes against a `0x190000` app partition, leaving `0x2050` bytes. This is too little growth room for further features without a BLE-specific partition/profile change. See [C6 HIL evidence](../evidence/board-bringup/2026-10-01-ble-c6.json).

An original ESP32 HUZZAH32 BLE build still exceeds static DRAM by 13,488 bytes even with Art-Net, DDP, and E1.31 excluded. It was not flashed. The service is currently qualified on C6 only; the original ESP32 needs a smaller composition or static-memory refactor. ESP32-S3 and radio coexistence under sustained traffic remain untested.

The HIL loop exposed an existing task-stack bug: ESP-IDF 6.0.2 takes `xTaskCreateStatic` depth in **bytes**, but nine components passed a `StackType_t` array's element count. These calls now pass `sizeof(stack_array)`, using memory they already reserve. The serial stack was raised from 4 to 8 KiB after a reproducible NVS settings-write stack fault. The default six-board builds verify the changed task definitions.
