# 5.5 BLE control transport

The shared framing and dispatch layer has an opt-in NimBLE GATT service. Six board images build and have answered hardware BLE control requests. An opt-in Classic Bluetooth SPP profile now builds for the three original ESP32 boards and has answered control requests on HUZZAH32 and M5StickC. Longer cross-board radio coexistence remains open.

The existing BLIP control envelope can now be handled without serial COBS framing. The serial endpoint uses this shared handler, so BLE can submit the same binary request and receive the same binary response, including structured control errors and request IDs. A HUZZAH32 app build was flashed and its serial control probe passed after the refactor.

BLE GATT values use a four-byte header: flags (`START=1`, `END=2`), an 8-bit frame ID, and a little-endian 16-bit byte offset. The remaining bytes carry a slice of one raw BLIP envelope. The bounded assembler rejects missing, duplicate, reordered, oversized, and incorrectly flagged slices. A new `START` can recover from an abandoned partial request. Response slices advance only after an acknowledgement, so the service can send responses as indications. Host tests round-trip the maximum envelope with 20-byte GATT values (default ATT MTU 23), then exercise ordering and bounds failures.

`BLIP_ENABLE_BLE` defaults to off. The ordinary firmware build excludes the BLE GATT source and NimBLE configuration. Opting in selects `sdkconfig.ble.defaults`, which enables one peripheral connection and removes unused central, observer, and broadcaster roles. It defaults Art-Net and DDP off on the 4 MB boards to leave app space; the 8 MB Creators Ball keeps them on. `blip.transport.ble.enabled` is persisted and defaults to false. Disabling it waits for any response indication to be acknowledged, then stops advertising and deinitializes NimBLE; serial control remains available. The BLE worker uses an 8 KiB dynamic task stack: a 4 KiB worker overflowed while saving settings over GATT on M5Dial.

The service UUID is `6a6a83c0-64cf-43f4-8a3a-8bd713d24300`. Its RX characteristic at suffix `4301` accepts acknowledged writes, and its TX characteristic at suffix `4302` sends indications. Control dispatch runs in a separate worker task, outside the NimBLE host callback. The service exposes active, advertising, connected, subscribed, received-request, acknowledged-response, and rejected-chunk readbacks. `v2/tools/control/blip_ble_control.py` scans, connects, fragments requests to the negotiated MTU, reassembles indications, and decodes structured control responses.

The XIAO ESP32-C6, Creators Ball V2, HUZZAH32, Creators Tab, M5StickC, and M5Dial each flashed an opt-in image and answered a GATT control request. BLE probe writes were checked by serial readback on every board. BLE disable and serial re-enable were checked on every board, though Tab's Wi-Fi was suspended for the first clean round trip. The earlier [C6 foundation evidence](../evidence/board-bringup/2026-10-01-ble-c6.json) and [six-board follow-up](../evidence/board-bringup/2026-10-01-ble-six-board.json) give the build sizes and limits.

On original ESP32, the controller's reserved DRAM prevented a static OSCQuery component and worker stack from linking. The BLE worker stack is now dynamic, and the ESP32 BLE profile allocates OSCQuery's fixed buffers from the heap at boot. HUZZAH32 reports about 41 KiB free internal heap with BLE and Wi-Fi active; its minimum during the probe was about 24 KiB. The browser root still returned HTTP 200 over shared Wi-Fi. This is a constrained profile and needs a longer mixed-traffic soak.

Creators Ball V2 reports 8 MB flash and uses `partitions-8mb.csv` when BLE is included, giving two 3 MB OTA app slots. The 4 MB XIAO C6 BLE profile uses `partitions-ble-4mb.csv`: two `0x1a0000` app slots and a 512 KiB LittleFS partition. Its `0x18df60` image leaves `0x120a0` bytes per app slot; the browser root and BLE control both responded after factory flash. These partition layouts differ from the ordinary 4 MB layout, so switching an installed device to either profile requires a factory flash of the bootloader, partition table, app, OTA initialization data, and storage image. The browser installer builder now creates separate checked factory packages for these C6 boards; the merged-image checks are recorded in the [installer evidence](../evidence/browser-installer/2026-10-01-ble-c6-packages.json). The [shared-network OTA check](../evidence/board-bringup/2026-10-01-ble-c6-ota.json) passed on both layouts. Ball had one BLE-active timeout, then successful attempts with BLE suspended and active. Web Serial installation remains open.

Creators Tab repeatedly brownout-reset during Wi-Fi association with BLE active at Wi-Fi TX profile `2` (19.5 dBm). Profile `0` (15 dBm) allowed a short BLE write/readback and browser HTTP 200 check, but a longer observation still accumulated brownout resets (boot sequence 2 to 6, reset cause `brownout`). A proposed automatic TX cap was removed because it did not solve the problem. BLE was disabled and the original TX profile restored on this board after testing. With BLE disabled, its boot sequence stayed at 4 over the final observation. Reliable simultaneous Wi-Fi and BLE needs a stronger power source or a different board-level power policy before qualification.

Ball remained reachable with BLE active during an OTA attempt, but the upload client timed out after 300 seconds. The same image was accepted in about 10 seconds after BLE was suspended, then confirmed after reboot. A later BLE-active OTA of that image also succeeded and confirmed after reboot. The cause of the first timeout remains unknown.

An 8 MB Ball build with BLE, Art-Net, DDP, and E1.31 enabled passed a [three-minute shared-network soak](../evidence/board-bringup/2026-10-01-ball-ble-network-soak.json): all 3,686 packets sent per protocol were accepted, applied LED frames rose from 1 to 5,765, failed frames stayed at zero, and free internal heap ended within 36 bytes of its starting value. BLE GATT reads succeeded during the traffic. This validates the counters and bounded memory behavior for that run; it does not establish waveform timing or longer-term reliability.

`BLIP_ENABLE_CLASSIC_BT` selects a separate Bluedroid SPP build for original ESP32; it cannot be combined with NimBLE or selected on S3/C6. The SPP service uses the same COBS-framed control envelope as USB serial. Its persisted `blip.transport.classic.enabled` setting defaults to false. HUZZAH32 and M5StickC flashed Classic images, answered SPP get/set requests, matched SPP writes by serial readback, and passed live disable and serial re-enable. HUZZAH32 also restored the saved enabled state after reset and rejected a malformed frame before answering the next valid request. Twenty consecutive SPP connections returned control responses with no sustained loss of free internal heap. [Classic HIL evidence](../evidence/board-bringup/2026-10-01-classic-spp.json) records build sizes and heap. The Creators Tab image builds, but radio coexistence on its present power connection has not been qualified. The original ESP32 Classic profile places its LED component, and HUZZAH32's sleep component, on the heap to fit Bluedroid's fixed DRAM reservation. The HUZZAH32 has only about 14–16 KiB free internal heap with Classic active, so longer sustained traffic remains open.

The HIL loop exposed an existing task-stack bug: ESP-IDF 6.0.2 takes `xTaskCreateStatic` depth in **bytes**, but nine components passed a `StackType_t` array's element count. These calls now pass `sizeof(stack_array)`, using memory they already reserve. The serial stack was raised from 4 to 8 KiB after a reproducible NVS settings-write stack fault. The default six-board builds verify the changed task definitions.
