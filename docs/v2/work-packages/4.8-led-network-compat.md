# Work package 4.8: network lighting compatibility

Art-Net, E1.31, and DDP live in separate ESP-IDF components (`blip_artnet`,
`blip_e131`, and `blip_ddp`). The firmware registers Art-Net and DDP by default
on all six board builds. `BLIP_ENABLE_ARTNET=OFF` and `BLIP_ENABLE_DDP=OFF`
independently remove their components and registry entries from an ESP-IDF
build. Six ESP32-C6 feature combinations and their component-closure results are in
`docs/v2/evidence/board-bringup/2026-10-01-lighting-feature-build-matrix.json`.
The default dual-protocol image also builds for all six board definitions;
those artifact hashes and component checks are in
`docs/v2/evidence/board-bringup/2026-10-01-artnet-ddp-six-board-builds.json`.
`BLIP_ENABLE_E131=ON` adds the optional E1.31 runtime; its default is OFF.
All six three-protocol builds and the E1.31-only/all-off component checks are in
`docs/v2/evidence/board-bringup/2026-10-01-e131-six-board-builds.json`.
Parsers validate identifiers, protocol versions, lengths, universes, start
codes, and offsets before exposing a bounded payload view.

Art-Net accepts Poll, ArtDmx, and ArtSync and emits a complete 239-byte PollReply
containing IP, names, OEM, universe, port direction, MAC, and DHCP capability.
`EspArtNetComponent` owns a static UDP task on port 6454, answers ArtPoll at the
requesting controller with the current station IP and MAC, maps ArtDmx into the
registered LED output's bounded stream surface, and exposes accepted, rejected,
and discovery counters. Host tests cover packets and discovery fields; socket
work stays outside LED submission. A Creators Ball V2 answered unicast and
directed-broadcast ArtPoll, accepted bounded ArtDmx, and advanced the LED frame
counter. The user also observed red fades and on/off behavior on the Ball LEDs
during the network lighting tests. The hardware evidence is in
`docs/v2/evidence/board-bringup/2026-10-01-creators-ball-artnet.json`.

`EspE131Component` binds UDP 5568 and joins the multicast group for universe 1
when station Wi-Fi connects. It also accepts unicast data. The fixed two-source
receiver tracks source IDs, sequences, priorities, stream termination, and a
2.5-second source timeout. Equal-priority sources merge by highest channel
value; higher priority wins. Output is trimmed to the configured pixel count
before the locked LED stream handoff. Preview and synchronized packets are
ignored and counted; synchronization packets are not implemented. Source
capacity, malformed input, output rejection, and multicast join failures are
observable. Ball hardware received unicast and multicast data with no output
rejection; the reproducible counters are in
`docs/v2/evidence/board-bringup/2026-10-01-creators-ball-e131.json`.
Other-board E1.31 hardware checks and sustained timing qualification remain open.
The packet layout and universe multicast mapping follow
[ESTA's E1.31 standard](https://tsp.esta.org/tsp/documents/docs/E1-31-2018.pdf);
the IPv4 membership setup follows
[Espressif's UDP multicast example](https://github.com/espressif/esp-idf/blob/master/examples/protocols/sockets/udp_multicast/main/udp_multicast_example_main.c).

`EspDdpComponent` is registered on all six board builds. It binds UDP 4048,
accepts destination 1 RGB8 DDP packets (including the legacy RGB8 type),
tracks 4-bit sequence wrap, and reports accepted, invalid, stale, and output
rejections separately. The task passes validated updates to the LED worker
through a bounded, mutex-protected stream surface. The RMT output path now
composes and encodes the stream for the configured WS2812/SK6812 pixel count;
an out-of-range update is rejected.
Five connected boards passed short DDP receive
and output-counter checks; the M5StickC image built but its serial port is
currently absent. These results are recorded in
`docs/v2/evidence/board-bringup/2026-10-01-ddp-six-board-rollout.json`.
