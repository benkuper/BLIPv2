# Persisted network controls and transport stack qualification

- Date: 2026-10-09
- Status: six-board focused checkpoint; broader milestone qualification remains open
- Evidence: [transport stack trials](../evidence/web/2026-10-09-transport-stacks.json)

Repeated device-name saves over UDP exposed an OSC task stack overflow beneath
NVS page collection. The first probe failed on its first persisted write; moving
reply-copy scratch out of dispatch let several cycles pass, but collection still
overflowed the original 6 KiB stack. Both failures are retained in the evidence.

OSC routing now resolves only a dynamic control's kind and generation. The
dispatcher still acquires and validates its complete schema before admission;
duplicating those descriptor/field arrays in the endpoint was unnecessary.
Reply string copying uses a separate non-inlined embedded call, retaining owned
and overlapping-string behavior without carrying its 512-byte scratch through
settings writes. The ESP32 dispatch frame fell from 2,128 to 1,424 bytes.

The OSC task now reserves 8 KiB, covering measured NVS collection paths. The
Wi-Fi configuration worker reserves 4 KiB instead of 6 KiB. Their combined
reservation and each reference board's measured static BSS are unchanged.
Serial remains at 8 KiB: script admission reached sufficiently deep paths that
reducing that stack would remove its measured reserve. Serial frame counters
and stack headroom are now read-only parameters visible in Advanced mode.

The new `blip_transport_stack_hil.py` exercises 20 cycles each over UDP and
WebSocket: persisted identity and LED writes, Wi-Fi settings commits, owned
dynamic script strings, typed guest actions, result checks, serial provisioning
and deferred HTTP provisioning. It verifies the installed board/release, no
unexpected reboot, at least 1 KiB headroom per measured task, and restoration of
the original settings. It journals those settings before mutation, captures
serial output and can reopen native USB during cleanup. Credentials come from
the ignored local provisioning file and are excluded from reports. PC Wi-Fi
never changes.

These readings include the workload and restoration, rather than a guarantee
for every future workload. M5Dial's HTTP reserve is close to the 1 KiB gate;
future routes must retain or improve it. All seven code-15 production profiles
compile, all 33 host suites pass, and the three-family baseline script-control
trials pass. Code 15 remains installed on the six working boards.

Ball's first two native code-12-to-15 downloads failed with
`artifact-transfer-or-validation`; the captured repeat identifies an HTTP
`body-read` failure and socket-not-connected errors. Its code-15 installation
used the generated 8 MiB factory flash arguments instead. HUZZAH32 and M5Dial
passed native code-15 updates. Ball retains its external SD UI (code 3106) and
default device name. The native firmware checker now records serial diagnostics,
initial heap and partial download progress even on failure.

Ball's full BLE/WASM/external-SD profile still has substantial update-memory
pressure under browser traffic. After the stack probe, free heap recovered as
connections expired, but the largest block remained smaller than a fresh update
worker reservation; live browser connections also remain present. This is an
open coexistence issue. No capability was removed to pass these tests, and this
checkpoint does not close the broader update, storage or full milestone gates.

On 2026-10-09 the user removed Creators Tab from all checks because no working
unit remains. Its previous flash-access failure is retained in the historical
JSON and no longer blocks this six-board matrix.
