# 5.6 V2 ESP-NOW control transport

`BLIP_ENABLE_ESPNOW=ON` includes the transport; the ordinary build excludes it.
The component is disabled in settings until a station MAC is assigned to
`blip.transport.espnow.peer_mac` and `enabled` is set to true. The Wi-Fi station
must be connected. ESP-NOW follows its current channel, so the two peers can
remain on the same infrastructure Wi-Fi while the computer keeps Internet
access. Live disable deinitializes ESP-NOW; it does not stop Wi-Fi or BLE.

The V2 packet header is 16 bytes: `BN`, version 2, data/ACK kind, a random
32-bit boot session, a nonzero 32-bit sequence, total message size, fragment
index and fragment count. Integers are little endian. A radio packet is at most
250 bytes, with up to 234 envelope bytes per data fragment. The 536-byte BLIP
control envelope therefore takes at most three fragments. Reception accepts
out-of-order fragments, rejects contradictory repeated fragments, bounds its
buffer, and dispatches a completed sequence once. A duplicate completed
sequence is ACKed again without repeating the control operation. ACKs name
the session and sequence of the complete message. A sender retries the whole
message after 250 ms, up to six transmissions. Responses use the same framing
and acknowledgement rules.

The configured peer can receive any V2 control envelope. `remote_read` and
the typed `remote_write*` actions initiate a single request from local serial,
OSCQuery, or another local control client. One peer and one outbound request
are supported at a time. No V1 ESP-NOW packet is parsed or emitted. Existing
imported V1 ESP-NOW settings records are ignored; a new V2 record is written
when the peer or enable switch is changed.

The peer MAC filter is an address selection mechanism, not authentication.
ESP-NOW payloads in this profile are unencrypted, including remote writes.
Use it only on a radio network where that is acceptable. Key provisioning and
authenticated peer control remain separate work.

## Verification

`blip_espnow_frames_tests` covers maximum-size fragmentation, reordering,
loss and whole-message retry, lost ACK, duplicate suppression, malformed
packets, stale ACKs, and sequence wrap. Both an XIAO ESP32-C6 and a Creators
Ball V2 exchanged remote reads and integer writes on shared Wi-Fi. A 262-byte
control envelope crossed as two ESP-NOW fragments and was dispatched once.
Disabling the Ball caused bounded retries on the XIAO; re-enabling it restored
the link while Ball BLE remained active. The Ball then exchanged bidirectional
reads and typed integer writes with HUZZAH32, M5StickC, Creators Tab, M5Dial,
and Creators Club; all five links returned direct serial readbacks with zero
ESP-NOW retries. All seven opt-in builds fit their app partitions. Evidence is in
[`2026-10-01-espnow-v2.json`](../evidence/board-bringup/2026-10-01-espnow-v2.json).

The seven-board build and peer gate passed. Longer radio soak and authenticated
peer control remain open. The Club's short red and stream checks completed
without driver failures. A later visible check cycled red, green, and blue twice
at brightness 32/255, holding each color for five seconds. The user confirmed all
LED sections showed the correct colors steadily; the driver recorded 18 applied
frames and zero failures. The strip was blacked out and disabled afterward.

After these checks, a later reset of the Club booted V1. Readback showed its
bootloader, partition table, and app0 headers no longer matched the V2 image;
the user confirmed that their parallel work on the Club's V1 firmware caused
the reflash. The V2 profile was subsequently installed again for the visible
color check and provisioned back onto shared Wi-Fi.
