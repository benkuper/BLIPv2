# Update recovery and browser connection checkpoint

- Date: 2026-10-09
- Status: implementation and focused HIL checkpoint; milestone qualification remains open
- Requirements: [web and self-update scope](3.7-device-web-and-self-update.md)
- Evidence: [recovery and coexistence trials](../evidence/web/2026-10-09-update-recovery.json)

The native release downloader now has socket capacity alongside the HTTP server,
OSC and lighting transports. The former ten-socket SDK configuration failed to
allocate its outbound connection with a browser and three other HTTP sessions.
The default is sixteen; CMake rejects stale smaller configurations. A HUZZAH32
map comparison measured 360 additional static BSS bytes, with unchanged static
data. No authentication or encryption was added.

UI 0.3.5 (code 3005, 26,475 bytes) reconnects an evicted WebSocket automatically.
Retries start at 500 ms, double to a ten-second cap and reset on successful
connection. Explicit disconnect cancels retries; obsolete sockets cannot change
the new connection or deliver stale controls. Reconnection preserves the current
view and editors. Successful web installation still intentionally refreshes the
page to load the new assets. The full bundle remains outside the application.

The native file backend disables redundant stdio buffering: callers already
provide bounded chunks and FAT/LittleFS cache their own sectors. Durability still
requires flush, fsync, close and the existing verified generation trailer. Memory
and open-file exhaustion have distinct errors. Serial diagnostics now retain the
underlying update and SD read/write failure details, separating write rejection,
busy timeout and status failure.

`blip_release_recovery_hil.py` serves a local fault catalog on the existing LAN.
It injects malformed/oversized/incorrect-identity/redirect catalogs, incorrect
artifact identity and SHA, truncated transfers, web CRC corruption, cancellation
and hardware reset during downloads. It checks retained firmware/UI/name and
storage medium. An optional real-browser observer checks connection recovery,
the single intentional asset refresh and final live control under extra HTTP
sessions. The harness waits for station readiness, records initial policy before
mutation and restores it even when a browser assertion fails. It never switches
PC Wi-Fi. An earlier observer incorrectly treated the initial Offline label of
the intentional page reload as a failure; that bounded reload is now distinguished
from a connection outage.

The public release handler and local simulator now serve devices concurrently.
A slow firmware download previously blocked catalog checks for other boards for
longer than the device's five-second HTTP timeout. The regression fixture stalls
an eight-MiB artifact reader and checks a second catalog connection independently.
This changes the separate API server only; it adds no device-side dependencies.

Focused results at this checkpoint:

- HUZZAH32 and M5Dial each passed the full 128-check fault/recovery/browser
  matrix. Each also passed the 12-check native firmware upgrade to code 10.
- Ball passed native web installation on external SD (13 checks) and all three
  families passed the 51-check file-storage suite, including reboot persistence.
- Ball's code-9-to-10 transfer interrupted the checker's native USB write handle.
  A separate eight-check observation confirmed code 10, confirmed boot, exactly
  one software reboot, retained name/UI/external medium and HTTP version. The
  original checker report remains failed. The helper now reopens transient USB
  handles without resetting the board and journals policy before changing it.
  Its subsequent code-10-to-11 native upgrade passed all 12 checks and restored
  the original policy. Code 11 remains installed on Ball; code 10 remains on
  HUZZAH32 and M5Dial.
- Ball's current external-SD fault matrix remains incomplete: the repeated trial
  reached 85 passing checks before worker-memory admission failed. Browser plus
  extra HTTP sessions can also exhaust the worker's contiguous allocation.
  An earlier code-4 Ball run passed the fault portion but did not record its
  physical medium; it does not qualify the newer external-SD case.
- All seven production profiles compile. Host tests passed 33 suites, JS passed
  32 tests, release-server tests passed ten tests and foundation validation passed
  ten checks. Original documented endpoint/24-hour/automatic-update policies were
  restored and verified on all three reference boards.

Focused hardware results and precise artifact/report hashes are in the evidence
record. These trials do not imply seven-board milestone completion. Creators Tab
still requires recovery of its unreadable flash. C6 browser/update RAM pressure,
lighting/BLE/fleet coexistence, first-run failure recovery, full external-media
qualification and remaining application/UI integration stay open.
