# Work package 6.1: WASM runtime benchmark

- Date: 2026-10-07
- Result: benchmark and runtime-selection deliverables complete
- Decision: [ADR-0008](../adr/0008-wasm-runtime-selection.md)
- Evidence: [nine target runs](../evidence/wasm/2026-10-07-runtime-benchmark.json)

The standalone [qualification project](../../../v2/qualification/wasm/README.md)
builds native, WAMR and wasm3 variants from pinned releases. It measures linked
flash/RAM, native and Wasm stacks, load/steady heap, arithmetic, pixel stores,
host calls, checked results, memory initialization/growth and fault recovery.
Its higher-priority supervisor tests infinite loops without depending on the
interpreter returning. Build scripts reuse the SDK build for each chip and
archive independent images/ELFs/maps/configuration/size data.

All nine images built and ran on XIAO C6, M5Dial S3 and HUZZAH32 ESP32. All normal
workloads and non-loop traps passed. WAMR terminated a 10,000-instruction loop
in 3.02–3.88 ms and accepted a subsequent valid call. wasm3 required a board reset
on each target. WAMR remains the selected runtime, with its fast interpreter,
instruction metering, software bounds checks and pool allocation. Its measured
76,992 used pool bytes are separate from the 128 KiB reservation.

The native baseline executes actual non-inlined host calls and observable pixel
stores. Both engine configurations keep validation/stack checks enabled. Local
port adaptations are explicit in the recipe; upstream runtime checkouts remain
unmodified. The collector rejects incomplete output, failed results, missing
restore verification and mismatched image hashes before writing evidence.

The test runner restored production BLIP images after each board's trial and
verified serial replies. The PC's network was not switched. Other boards were
not flashed: this qualification contains no board pin/output logic and tests one
representative per supported processor family. Production feature/profile
compatibility will receive its own seven-board gate after the service works.

This completes the 6.1 artifacts, not Gate D or the full implementation Plan.
Production coexistence, lifecycle heap trends, module/provider bounds and the
remaining script ABI/SDK work stay open. Existing physical Gate C qualification
also remains open; benchmark progress does not change that evidence boundary.
