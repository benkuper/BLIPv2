# Work package 6.3: Supervised production WASM worker

- Date: 2026-10-07
- Result: opt-in worker and Ball coexistence slice passed; full qualification open
- Contract: [ADR-0010](../adr/0010-wasm-production-worker.md)
- Evidence: [Ball production trial](../evidence/wasm/2026-10-07-production-worker-ball.json)

## Implemented

The production entry point can register `EspWasmComponent` with
`BLIP_ENABLE_WASM=ON`. It injects the runtime-neutral adapter, supplies fixed
buffers and gates control admission until normal boot confirmation. Safe mode
does not start the script worker. Existing profiles keep WASM off by default.

Owned asynchronous requests cover contiguous CRC-checked uploads, passive load,
typed calls and unload. The eight-request queue rejects overload; sixteen
completions retain numeric result bits and error codes. IDs do not repeat.
Epoch cancellation invalidates active/queued/upload work, and captured module
generations prevent queued calls from executing after a replacement/unload.
Control parsing/polling never invokes guest code inline.

The worker runs at priority 2 with an 8 KiB native stack. A priority-6 supervisor
with 4 KiB stack observes deadlines/epochs every 1 ms and repeatedly requests
active cancellation, covering the admission/publication race. Instruction fuel
is enforced independently. Late results are discarded and the instance requires
reload. Stop disables admission, cancels, joins and frees buffers only after
quiescence. Native task stop/restart still needs its own hardware qualification.

## Memory and production configuration

The full Ball BLE/fleet/network profile initially could not allocate a contiguous
96 KiB pool. Moving optional Wi-Fi fast paths out of IRAM and bounding packet
buffers allowed startup, but concurrent network traffic then reached only
1.7 KiB free heap. Production now reserves **80 KiB engine pool**, **16 KiB
module scratch**, and **12 KiB native task stacks**. The one-page linear memory
and 4 KiB Wasm stack are inside the engine pool. Peak engine use was **72,176
bytes**. A valid input below the 16 KiB admission limit can still exceed decoded
pool capacity and must fail explicitly.

The aligned pool allocation is explicit; ordinary SDK heap allocations only
guaranteed four-byte alignment on the C6. The adapter also uses the SDK's stack
start API without requiring FreeRTOS trace facilities. A 1,000 Hz tick rate is a
build requirement. `sdkconfig.wasm.defaults` applies the memory/tick profile;
use a fresh build directory because defaults do not override an existing config.

The final app is **1,806,320 bytes** in a **3,145,728-byte** partition. Compared
with the prior qualified Ball profile (`7a0f270`), it adds **99,088 app bytes**.
This comparison includes the Wi-Fi/tick profile changes and is not an isolated
engine delta. Linked DIRAM contains **111,768 BSS bytes**, **24,464 data bytes**
and **97,436 code bytes**. Heap reservations and native stacks are separate
from those linked sizes; the evidence records both.

## Validation

All **22 host test executables passed**, including bounded upload order/size,
CRC failure, cancellation and recovery cases. The final production Ball trial
passed **124 checks**, covering:

- Numeric result bits, unreachable/OOB/divide/recursive-stack traps and fuel.
- Rejection of automatic entry points, imports and oversized linear memory.
- Active and queued cancellation, reject-new queue overload and stale generations.
- Partial upload cancellation, completion expiry and recovery through reload.
- Twenty load/call/unload cycles with exactly constant SDK heap after warmup.

The same full production image then ran twenty infinite-loop calls with a
50 ms deadline while serial probes, persisted LED settings writes, DDP traffic
at a requested 60 Hz and OSCQuery HTTP requests continued. During that window:

| Measurement | Result |
| --- | ---: |
| DDP packets sent / accepted | 148 / 145 |
| LED applied-frame increase | 149 |
| LED failed-frame increase / DDP output rejections | 0 / 0 |
| HTTP successes / failures | 9 / 0 |
| Maximum HTTP response time | 321.5 ms |
| Persisted settings writes | 20, original setting restored |
| Maximum completion time for a 50 ms script deadline | 99.4 ms |
| Free internal heap after traffic / boot-lifetime minimum | 36,096 / 16,876 bytes |
| Worker / supervisor native stack headroom after traffic | 5,168 / 3,464 bytes |

These are measured operational counters, not lossless UDP, exact deadline or
physical LED timing guarantees. Deadline cancellation and late-result rejection
are enforced; higher-priority SDK/cache work can delay worker completion. Longer
soaks and latency qualification remain necessary.

The PC and board initially occupied different subnets. The network wrapper used
a temporary clone of the saved guest profile and a verified, independent
45-second recovery process. It waited for device TCP reachability after DHCP,
then restored the original `Archi-Wifi` connection, verified Internet access and
removed the temporary profile. No credential password is in the evidence.
The Ball retains the production test image; other boards were not flashed here.

## Reproduction

Build the Ball in a fresh directory using ESP-IDF 6.0.2 and the pinned WAMR:

```powershell
idf.py -C v2/firmware -B build/m6-production-ball `
  -D IDF_TARGET=esp32c6 -D BLIP_BOARD_CREATORS_BALL_V2=ON `
  -D BLIP_ENABLE_WASM=ON -D BLIP_ENABLE_BLE=ON `
  -D BLIP_ENABLE_ESPNOW=ON -D BLIP_ENABLE_FLEET=ON build
```

Provision the local credentials with `blip_wifi_provision.py`. Use
`blip_wasm_hil.py --port COM10 --board creators-ball-v2 --build <build>
--output <report> --ip <reachable-ip> --pixels 36`. If a PC network switch is
required, use `blip_wasm_network_hil.ps1` and its independent recovery safeguard.
The evidence collector validates results, source/build hashes, pool/stack/heap
limits, runtime pin and network restoration before saving the aggregate.
