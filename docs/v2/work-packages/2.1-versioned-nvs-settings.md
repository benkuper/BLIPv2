# Work package 2.1: Versioned atomic NVS settings

- **Status:** implementation and host/build verification complete; merge remains
  gated by the open Gate A hardware rows `A-04` through `A-06`.
- **Depends on:** Gate A and ADR-0005.
- **Scope:** `blip_storage`, its host simulator/tests, and bootstrap registry
  integration.

## Compatibility disposition

- **Preserved:** V1 source, public OSC paths, and the V1 NVS namespace/key
  `blip/settings` are unchanged. The V2 backend never erases NVS automatically.
- **Changed for V2:** settings are independent opaque payloads per stable
  component ID, and every record carries a format version, component ID,
  component settings schema, generation, explicit lengths, and CRC-32.
- **Deferred:** typed parameter serialization, ordered schema migration, and V1
  MessagePack import belong to work package 2.3. LittleFS/SD atomic replacement
  belongs to 2.2.
- **Removed:** no public V1 behavior or format is removed by this package.

## Service contract

`SettingsStore` accepts a registry `ComponentDescriptor`, so the stable component
ID and current settings schema remain registry-owned. Payload encoding is opaque
to storage and returned byte-for-byte; this lets later migration code retain
unknown fields instead of having the storage layer reinterpret them.

The caller owns one fixed scratch span. The production service supplies 4,096
bytes, allowing `4,064 - component_id_length` payload bytes. Calls are serialized
on the storage/maintenance scheduling class. The store itself allocates no heap,
creates no task, and performs no logging. The ESP-IDF NVS implementation may use
IDF-internal startup heap.

The registry component is `blip.storage.settings`, provides
`storage.settings`, requires no pins, buses, DMA, PSRAM, or radio, cannot be
disabled live, and creates no task. Its declared budget is 24,576 bytes linked
code/data, 4,864 bytes static internal RAM including the scratch reserve, and
zero task-stack bytes.

## NVS names and byte format

The backend uses NVS namespace `blip_v2`. Each component has three 13-character
keys: `a<hash48>`, `b<hash48>`, and `c<hash48>`, where `hash48` is the low 48
bits of the component ID's 64-bit FNV-1a hash in lowercase hexadecimal. Slot
records contain the full component ID and commit records contain the full
64-bit hash, so a truncated-key collision is detected rather than silently
loading another component's settings.

All integers are little-endian. The CRC is standard IEEE CRC-32 over the entire
record while treating its own four-byte field as zero.

### Slot record `BLPS`, format 1

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLPS` |
| 4 | 2 | record format version (`1`) |
| 6 | 2 | fixed header size (`32`) |
| 8 | 4 | component settings schema version |
| 12 | 8 | monotonically increasing generation |
| 20 | 2 | component ID byte length |
| 22 | 2 | flags, currently zero |
| 24 | 4 | payload byte length |
| 28 | 4 | CRC-32 |
| 32 | variable | UTF-8 component ID bytes followed by opaque payload bytes |

### Commit record `BLPC`, format 1

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLPC` |
| 4 | 2 | record format version (`1`) |
| 6 | 2 | record size (`32`) |
| 8 | 8 | full 64-bit component ID hash |
| 16 | 8 | committed generation |
| 24 | 1 | selected slot (`0` = A, `1` = B) |
| 25 | 3 | reserved, zero |
| 28 | 4 | CRC-32 |

The host suite includes a golden byte vector for both records and the derived
NVS keys, preventing encoder/decoder changes from silently redefining format 1.

## Save and recovery rules

1. Inspect and validate both slots and the commit record.
2. Choose the active committed slot when its generation matches. With a missing,
   torn, or stale commit, choose the highest valid slot deterministically.
3. Write the next generation to the inactive slot and commit that NVS write.
4. Read it back; verify magic, version, lengths, component identity, schema,
   generation, payload bytes, and CRC.
5. Write and commit the commit record, then read it back and verify it.
6. Retain the previous slot until a later successful save overwrites it.

An interruption before the commit update loads the previous committed value. An
interruption after the marker becomes durable loads the new value. A torn marker
selects the highest valid slot; a corrupt selected slot falls back to the other
valid generation. If no generation validates, load returns a typed
`corrupt_data` error rather than defaults. NVS-full, capacity, I/O, version, and
generation-exhaustion failures are also typed.

## Verification

The C++ host suite contains nine storage tests covering:

- empty-store behavior, version/schema round trips, slot rotation, and the
  independent golden byte layout;
- failure immediately before and after both durable writes;
- torn commit recovery and corrupt selected-slot fallback;
- corrupt-only-record diagnosis, per-component isolation, scratch/output bounds,
  and simulated NVS-full behavior.

All four CTest executables pass (28 logical tests total). BLIP-owned code passes
the pinned clang-format 18.1.8 check and warning-as-error builds with exceptions
and RTTI disabled. Clean ESP-IDF 6.0.2 builds pass the firmware contract on
ESP32, ESP32-S3, and ESP32-C6. Two independent clean build trees per target

## Rollback and migration

Rollback is the prior firmware artifact. V1 data remains untouched in its own
namespace. Removing this component leaves `blip_v2` records dormant; it does not
erase them. Work package 2.3 adds the ordered migration registry and read-only,
journaled V1 import while retaining this downgrade behavior.
