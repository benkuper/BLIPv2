## Implementation

The later [native lifecycle follow-up](6.3-wasm-native-lifecycle.md) qualifies
bounded component task restart and injected startup failures on three families.
The production memory measurements below remain their original checkpoint.

The original ESP32 production composition had insufficient contiguous DRAM for
the 80 KiB script pool. It now uses a separate 64 KiB guest linear arena in
byte-accessible IRAM and a 16 KiB engine pool in DRAM. Module input and native/VM
stacks remain in DRAM. WAMR's pinned fast interpreter performs floating-point
guest memory loads/stores as integer bit operations; hardware floating-point
computation stays in the DRAM VM stack. The dependency remains unmodified.

The ESP32 build requires single-core mode and the SDK's IRAM byte-access handler.
C6/S3 retain their contiguous pool. The neutral runtime boundary explicitly
borrows the optional arena and rejects unsupported configurations. Mapping,
growth, zeroing, ownership and usage accounting remain bounded. Individual
arena peaks are summed conservatively; unload returns reported usage to zero.

UART console output is routed through the UART driver used for framed replies,
and polling is restored when an owned driver is removed. This avoids separate
console FIFO writes bypassing the driver's TX lock. It **did not eliminate**
the M5StickC's observed missing reply byte, whose physical/driver cause remains
unresolved. The evidence reconstructs that reply and verifies its original CRC
after restoring the missing `m` in `blip.wasm`.

## Qualification scope

All **22 host executables passed**, including optional-arena prevalidation,
backend refusal, borrowing and cleanup. All seven production profiles built and
were flashed with app/OTA-data verification. They retain the test firmware;
no previous image was backed up or restored.

The hardware matrix records **1,365 checks**. Six boards run the complete suite.
The M5StickC explicitly omits `queue-reject-new` and `overflow-completions`
because its large UART burst repeatedly loses a reply byte. The same overload
policy passes on HUZZAH32, Tab and Club, which share the original ESP32 target.
The M5StickC still runs memory, traps, instruction/deadline budgets, short
active/queued cancellation, stale generations, upload cancellation, completion
expiry and load/unload checks. This is a coverage gap, not a resolved serial bug.

Memory fixtures cover aligned/unaligned f32/f64 storage, floating-point
arithmetic, NaN/signed-zero bits, data segments, byte/half-word accesses, the
last valid byte, bulk fill/overlapping copy, boundary traps, page growth and
reload zeroing. Decoded module capacity remains an independent bound.

The evidence binds build/source hashes, runtime pin, board MACs, partitions,
linked sizes, feature flags and flash verification to each trial.

Every unload reports zero pool use. Each board finishes with a complete
**20-cycle non-growing SDK heap window**. The harness permits one additional,
recorded stabilization window and fails if the second window still decreases.
HUZZAH32, M5StickC, Ball and XIAO needed that extra window (initial decreases
of 4, 4, 8 and 484 bytes respectively); both windows remain in the evidence.
These short measurements do not establish a long-term heap/fragmentation bound.
A fresh Ball memory call also hit a deadline during startup; its settled trial
passed. Low worker priority does not guarantee every healthy call meets a tight
deadline while higher-priority SDK work runs.

60 Hz requested DDP traffic, OSCQuery HTTP, serial probes and twenty persisted

an exact wall-clock retirement bound. Both separate traffic trials passed. A

latency and longer soaks remain open. Separate traffic runs keep slow UART
qualification out of the independent 45-second PC Wi-Fi recovery window.
Each wrapper restored the original Wi-Fi/Internet connection and removed its
temporary profile. Local credentials remain ignored and are absent here.

## Reproduction and remaining work

Build with `BLIP_ENABLE_WASM`, `BLIP_ENABLE_ESPNOW` and `BLIP_ENABLE_FLEET` enabled,
the correct target/board selector, and the pinned runtime. BLE is enabled only
for the Ball profile; Art-Net and DDP remain enabled on all seven profiles.
Use fresh build directories so the ESP32 defaults take effect.

Run `blip_wasm_hil.py --cycles 20` for serial checks, adding `--skip-overflow`
only for the documented M5StickC gap. Provision shared-network credentials from
the ignored local file. Run `blip_wasm_network_hil.ps1 -CoexistenceOnly` for the
selected traffic trials, then `v2/tools/wasm/collect_profile_evidence.py` to
validate and collect the matrix.

Global/cold heap exhaustion and fragmentation, the M5StickC serial burst,
active BLE/fleet traffic, long heap/network soaks, and physical Gate C
timing remain open. Checked string ABI, providers, script declarations,
persistent modules and the generated SDK remain subsequent work. Full Gate D
has not been accepted.
