# 5.4 Wi-Fi radio profiles and memory policy

The Wi-Fi network manager now separates two controls:

- `enabled` suspends or resumes Wi-Fi RF immediately. The driver remains initialized, so its memory is retained and the radio can resume without rebooting.
- `boot_profile` selects `0` (load Wi-Fi driver) or `1` (omit Wi-Fi netifs and driver) for the next boot. `active_boot_profile`, `profile_reboot_required`, and `driver_initialized` report what actually happened. The setting survives reboot in native Wi-Fi settings format 3; existing formats 1 and 2 default to the loaded profile.

The reclaimed profile keeps the ESP-IDF TCP/IP stack initialized because the other network components still create sockets. Its Wi-Fi driver and interface allocations are omitted. Static component buffers and lwIP allocations remain; this is a driver-memory policy, not a promise to recover all network memory. Wi-Fi is unavailable in that profile. Serial control stays active and can set `boot_profile=0` before rebooting to restore Wi-Fi. A profile change alone does not reset the live radio.

The browser receives the manager description from OSCQuery and displays it above the controls. Control labels explicitly identify the live RF switch, the next-boot profile, the active profile, driver allocation, and the pending reboot. The factory web bundle was regenerated and served from a HUZZAH32 on the shared LAN.

Host settings, OSCQuery, and web tests passed. All six board firmware profiles built. The HUZZAH32, Creators Ball V2, and M5Dial were flashed and each completed a reclaimed boot, served the full serial registry, and restored the loaded profile by serial plus reboot. Internal free-heap differences on these individual boards were 55,804, 63,408, and 57,936 bytes respectively. These values compare running states and are not isolated driver allocation measurements. See `docs/v2/evidence/board-bringup/2026-10-01-wifi-radio-profiles.json`.

BLE and ESP-NOW profiles are pending their transport implementations. The other three boards passed firmware builds but were not flashed for this policy cycle. The PC stayed connected to `Archi-wifi guest` throughout; no BLIP access point was used by the PC.
