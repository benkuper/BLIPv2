# Device web interface and self-update requirements

- Requested: 2026-10-08
- Status: required implementation; existing schema shell/local uploads are foundations
- Plan: work packages 3.7, 3.8, 3.9 and release work in 8.5
- Implemented checkpoints: [Simple/Advanced browser foundation](3.7-simple-advanced-foundation.md), [device identity](3.7-device-identity.md), [native updates and first run](3.8-native-update-and-first-run.md); full acceptance remains open

The finished device must serve a polished web app with two modes. Simple mode
provides the main controls and graphical live sensor/status views. Advanced mode
provides every parameter, action, event, diagnostic and resource assignment,
organized by topic and component with navigation, search and typed controls.
Both modes use the registry and retain live state when switching. Presentation
hints must support new components and dynamically loaded script controls.

Device identity is a required part of both modes: display the board's human-readable
type and its saved, editable device name. An unnamed device defaults to its type
(for example `Creators Club` or `M5 Dial`). mDNS uses a lowercase DNS-safe form of
the device name plus a stable MAC suffix to distinguish identically named units;
renaming updates discovery without a reboot. Non-ASCII/punctuation runs become
separators, with `blip` as the hostname stem if no ASCII letters or digits remain.
The display name itself retains valid UTF-8, up to 63 bytes. Save failures must
preserve the previously published name.

Milestone completion requires hardware validation on all seven connected boards:
Creators Club, Creators Tab, Creators Ball V2, HUZZAH32, XIAO C6, M5StickC and M5Dial.
Focused checks on affected boards are sufficient between milestones. Record
per-board evidence; successful builds alone are not hardware qualification.

Firmware and web assets must have independently visible installed/available
versions and independently selectable updates. Check the user-selected website
`https://www.goldengeek.org/blip/update?<info_in_GET>` with versioned public
compatibility metadata. An endpoint override is useful for development. Include
board, target, flash layout, profile/features, installed firmware/web versions,
API version and release channel. Exclude passwords, secrets and unnecessary
identifiers. Document and implement the machine-readable server response.

Initial web-interface installation must be easy: normal factory flashing writes
the complete web bundle directly into the filesystem image, with no separate manual
file upload and no full UI copy in the application binary. Also
provide a minimal firmware-resident first-run page that can download the interface
from the release endpoint automatically, install it atomically and refresh into
the full app, matching the V1 first-run experience. The first-run page must remain
available when the full interface is absent, and provide network setup and retry.

Web/server files, scripts, playback and sequence data use
[automatic media storage](2.2-automatic-media-storage.md). Board-declared external
flash/SD/MMC is preferred when mounted; internal flash provides the fallback.
File tools and update flows operate on logical names without asking the user to
choose a filesystem. Keep transactions on one medium and retain valid data on
failure or removal. Factory-installed web assets migrate through this same API.

Follow [ADR-0020](../adr/0020-private-show-network-defaults.md): public HTTP by
default, optional HTTPS, no required API credentials or signing. Validate device identity,
compatibility, sizes and hashes before activation. Keep downloads bounded.
Device-side checks/downloads must work without an open browser, with an explicit
install action and optional automatic policy. Coordinate updates with active
output. Firmware uses A/B boot confirmation/rollback; web assets use atomic
verified replacement. Preserve offline operation and recover from interruption.

Acceptance requires responsive phone/desktop layouts, keyboard accessibility,
actual graphical sensor updates, complete Advanced-mode coverage, automatic
dynamic-schema refresh, independent web/firmware updates, mismatch/corruption
rejection and on-device interruption/recovery tests on ESP32, S3 and C6.

The chosen URL returned HTTP 404 during the 2026-10-08 read-only endpoint check.
That observation does not establish a release API. The implementation must
provide its server contract/handler and qualify a local simulated release catalog.
The user will deploy the public endpoint online later; deployment is outside this task.
No update hosting deployment, signing key or remote release is claimed here.
