# Work package 6.3 follow-up: Native WASM worker lifecycle

- Date: 2026-10-07
- Result: production component lifecycle and injected startup cleanup passed on three chip families; full Gate D open
- Contracts: [ADR-0010](../adr/0010-wasm-production-worker.md), [ADR-0011](../adr/0011-esp32-wasm-linear-arena.md)
- Evidence: [native task lifecycle](../evidence/wasm/2026-10-07-native-worker-lifecycle.json)

## Scope

The minimal ESP-IDF qualification application links the production component,
runtime-neutral service and pinned, unmodified WAMR adapter. It retains the
production queue/completion capacities, 8 KiB worker and 4 KiB supervisor
stacks, priorities 2/6, 1 ms tick and each family's memory placement. A small
runtime decorator observes entry into the real guest invocation and forwards
execution/cancellation unchanged. The test caller runs at priority 7 so it can
fill the queue and request stop while the spinning guest is active.

The test checks cold startup, the control gate, rejection of double start,
idle/loaded shutdown, partial upload shutdown, restart, post-stop admission
denial, idempotent stop, retained completions, monotonic request IDs and heap
integrity. An active spin plus eight queued calls must all finish cancelled
with zero results; a ninth queued request must be rejected. A separate spin
must increment the real supervisor deadline counter and return no result.

One-shot linker wrappers are present only in the qualification executable.
They fail real engine/module/ESP32 linear allocations, supervisor creation,
the first or second SDK `pthread_create` bookkeeping allocation and worker
FreeRTOS creation. The second pthread allocation and worker task failures
exercise SDK cleanup of already allocated bookkeeping. Each failure must be
consumed exactly once, return the expected stage/error, retire tasks, release
buffers and allow a subsequent upload/call/start-stop cycle. Explicit backend
initialization rejection covers cleanup after both tasks have been created.

| XIAO / C6 | 1,225 | 6 | 30,004 us | 11,315 us | 5,400 / 3,796 B | 465,052 B |

All **3,716 checks** passed. Each family performed twenty complete native
start/upload/call/stop cycles with identical warmed DRAM, IRAM and task counts
after every cycle. Each injected startup failure and its subsequent recovery
returned to the same heap/task baseline. The ESP32's available IRAM returned
to 124,456 bytes each time. Heap measurements wait 50 ms after stop for the
FreeRTOS idle task to reclaim the self-deleting supervisor's storage.

The runner records chip/MAC identity, source hash, app/ELF/map/config hashes and
runtime pin. The collector validates these against local sources and build
artifacts. All three boards retain the validated test firmware. The PC network
was unchanged throughout the trials.

## Reproduction and limits

See the [qualification README](../../../v2/qualification/wasm-worker/README.md)
for build/run commands. Use fresh build directories for each family and the
current pinned runtime. The collector requires all three family reports.

The isolated application has substantially more free heap than the production
composition; the seven production memory trials remain a separate checkpoint.
Injected allocation rejection after warmup does not establish recovery from
global or cold OOM, lazy TLS/mutex allocation failure, a fragmented heap, or
every internal engine allocation failure. No production implementation or
vendor code was changed for fault injection. The measured stop/deadline
durations are observations under this workload, not hard real-time bounds.

Active BLE/fleet coexistence, long heap/network soaks, the M5StickC damaged
serial bursts and physical Gate C timing remain open. Checked strings,
capability providers, script declarations, persistence and generated SDK work
follow in 6.4–6.7. Full Gate D has not been accepted.
