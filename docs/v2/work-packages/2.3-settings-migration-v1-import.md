# Work package 2.3: Settings migration and V1 import

- **Status:** implementation, exhaustive host checks, reproducible three-target
  builds, and physical golden-import qualification complete.
- **Depends on:** ADR-0005, ADR-0006, work package 2.1, and the V1 settings
  fixture from work package 0.2.
- **Scope:** ordered V2 schema migrations, the bounded V1 MessagePack adapter,
  canonical imported-settings records, import journaling, and boot confirmation.

## Compatibility disposition

- **Preserved:** the V1 NVS namespace `blip` and blob key `settings` are opened
  read-only and are never erased or rewritten. Existing V2 component records
  win over imported values.
- **Imported:** all 112 values in the representative V1 fixture map into 22
  stable V2 component IDs and typed, versioned component payloads.
- **Changed for V2:** settings are split by component and wrapped by the
  transactional `BLPS`/`BLPC` records from work package 2.1. The import payload
  and journal are independently versioned.
- **Rejected:** unknown component paths, duplicate fields/components, malformed
  MessagePack, invalid UTF-8, non-finite numbers, oversized input, excess depth,
  and a changed source hash after a pending import all fail closed.
- **Removed:** no V1 data or behavior is removed by this package.

## Ordered V2 migrations

`MigrationRegistry` uses caller-owned step storage and buffers. Each step is a
pure `N -> N+1` transformation identified by component ID. Registration rejects
zero or non-consecutive versions, duplicate steps, missing callbacks, invalid
component IDs, and exhausted capacity. Execution requires every intermediate
step and alternates between the caller's output and scratch buffers. A payload
already at the requested schema is copied unchanged, making repeated execution
deterministic and idempotent.

The registry is infrastructure for component-owned migrations. No current V2
component advances beyond schema 1 in this package, so no invented semantic
conversion is registered.

## V1 boundary adapter

`LegacySettingsImporter` is a streaming, non-allocating parser for the single
documented V1 MessagePack shape. Its hard limits are:

| Limit | Value |
| --- | ---: |
| Source blob | 6,144 B |
| Nesting depth | 8 |
| Map entries | 64 per map |
| Components | 64 |
| Settings | 192 |
| Numeric array | 16 doubles |
| Component/field name | 48 UTF-8 bytes |
| String value | 256 UTF-8 bytes |

Integers retain signedness, strings must be valid UTF-8, floats must be finite,
and numeric arrays contain only exactly representable numeric values. The parser
first validates the whole source with no visitor, computes its SHA-256, and only
then allows the coordinator to write any V2 record.

## Canonical import payload `BLIV`, format 1

All integers and doubles are little-endian. CRC is standard IEEE CRC-32 over
the complete payload while treating its own four-byte field as zero.

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLIV` |
| 4 | 2 | format version (`1`) |
| 6 | 2 | fixed header size (`16`) |
| 8 | 2 | field count |
| 10 | 2 | reserved, zero |
| 12 | 4 | CRC-32 |
| 16 | variable | typed field entries |

Each entry contains a one-byte type, one-byte field-name length, two-byte value
length, UTF-8 field name, and value bytes. Defined types are Boolean, signed
64-bit integer, unsigned 64-bit integer, IEEE-754 double, UTF-8 string, and a
bounded array of doubles. Unknown fields remain present in the canonical payload
so later component decoders can retain or diagnose them rather than silently
discarding them.

## Journal and recovery

`LegacyImportCoordinator` imports one target component at a time through the
transactional `SettingsStore`. Before writing a target, it checks whether that
component already has any valid record; if so, it preserves that record. A reset
at any settings-store write boundary leaves a complete old or new record. The
next boot validates the same retained V1 source and resumes missing components.

The final target write is followed by a pending `BLPI` journal. Only after the
entire registry starts does the composition root rewrite the journal as
confirmed. Its format is:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | magic bytes `BLPI` |
| 4 | 2 | journal format (`1`) |
| 6 | 2 | record size (`64`) |
| 8 | 4 | importer version (`1`) |
| 12 | 1 | state (`1` pending, `2` confirmed) |
| 13 | 3 | reserved, zero |
| 16 | 2 | source setting count |
| 18 | 2 | source component count |
| 20 | 2 | preserved V2 component count |
| 22 | 2 | reserved, zero |
| 24 | 32 | source SHA-256 |
| 56 | 4 | reserved, zero |
| 60 | 4 | CRC-32 |

A confirmed journal with the same importer version and source hash makes later
boots read-only and idempotent. A journal from a newer importer or a different
source hash fails closed. Downgrade leaves the V1 source and V2 records intact.

## Memory and task policy

The production component owns 10,528 B of static storage: the 6 KiB source
buffer, two 1 KiB settings buffers, duplicate-detection workspace, numeric-array
workspace, and coordinator state. It creates no task and performs no direct heap
allocation. The recursive parser has a compile-time depth limit; the transient
ESP-IDF `main` startup stack is set to 8 KiB and is released when `app_main`
returns. Runtime components do not retain that stack.

## Rollback

Rollback is the prior firmware artifact. It ignores dormant `blip_v2` records
and continues reading the untouched `blip/settings` source. Removing the V2
import component does not erase either namespace. An explicit maintenance or
factory-reset action is required before either source or imported records can be
deleted.
