# V2 target profiles and quality gates

Passing a gate requires checked-in evidence. `planned`, `not-run`, an empty cell,
or a build from a different commit is not a pass. Measurements name the firmware
commit, manifest digest, ESP-IDF version, board/revision, power source, attached
peripherals, tool version, sample duration, and raw result artifact.

## Initial target profiles

Machine-readable manifests live under [`v2/profiles/targets/`](../../v2/profiles/targets/)
and validate against [`target-profile.schema.json`](../../v2/profiles/target-profile.schema.json).

| Profile | ESP-IDF target | Reference role | Gate-A requirement |
| --- | --- | --- | --- |
| `esp32-generic` | `esp32` | Original dual-core ESP32 compatibility and Classic Bluetooth-capable profiles | build, flash, boot, registry self-test |
| `esp32s3-generic` | `esp32s3` | USB-capable Xtensa reference | build, flash, boot, registry self-test |
| `esp32c6-generic` | `esp32c6` | RISC-V/Wi-Fi 6/BLE reference | build, flash, boot, registry self-test |

These are target profiles, not board pin maps. All pin assignments are explicitly
unset in Milestone 0. A board manifest may become `supported` only after its
schematic/pin source and bring-up record are committed. This avoids turning a
generic SoC profile into an unsafe board wiring promise.

Every target profile fixes these cross-target build contracts:

- ESP-IDF `release/v6.0` family, with the exact version and dependency lock
  committed by work package 1.1;
- C++20, exceptions disabled, RTTI disabled;
- warnings treated as errors for V2-owned sources;
- no production component selected in the Milestone 0 planning profile;
- all persisted/wire structures require a schema/protocol version;
- target-specific APIs stay behind capability interfaces.

## Evidence record states

| State | Meaning |
| --- | --- |
| `planned` | Test and threshold are agreed; implementation/evidence is not expected yet. |
| `pass` | Raw evidence exists and every threshold passed on the named commit. |
| `fail` | Test completed and at least one threshold failed. |
| `blocked` | Test could not execute; record states the external blocker and owner. |

Results are append-only records under `docs/v2/evidence/<gate>/<date>-<target>.json`.
Re-running a test adds a record; it does not edit away a failure.

## Foundation gates

| ID | Measurement | Pass threshold | Applies |
| --- | --- | --- | --- |
| `FND-01` | Offline foundation validation | all manifests, JSON, binary fixtures, hashes, cross-links, and generated bytes validate; exit code 0 | every commit |
| `FND-02` | Source scope | no V1 source path changed/moved/deleted in a V2 work package unless explicitly approved | every work package |
| `FND-03` | Reproducibility | two clean builds in separate directories produce identical application bytes after documented normalization | release profiles from 1.1 onward |
| `FND-04` | Optional feature accounting | each feature reports application flash, static DRAM/IRAM, boot-time heap, steady heap, task stacks, pins/buses, radio needs, conflicts, and live-disable policy | feature PRs |
| `FND-05` | Cost regression review | unexplained delta greater than 16 KiB app flash, 4 KiB static RAM, or 5% task-stack headroom blocks merge | feature PRs |

## Gate A — common core on all targets

| ID | Measurement | Pass threshold |
| --- | --- | --- |
| `A-01` | Clean CI build | minimal profile builds with zero warnings/errors for all three targets using the dependency lock |
| `A-02` | Boot readiness | registry validation and scheduler-ready marker within 3.0 s of reset, excluding network association |
| `A-03` | Lifecycle host suite | ordering, duplicate IDs, missing dependencies, cycles, partial-start cleanup, suspend/resume, and repeated stop all pass |
| `A-04` | Boot self-test | 100 cold boots per target with no panic, WDT reset, safe-mode entry, or registry mismatch |
| `A-05` | Internal memory reserve | after readiness and a 60 s warm-up: at least 64 KiB free internal heap and a 32 KiB largest free internal block in the minimal profile |
| `A-06` | Task stack reserve | every task retains at least 1024 bytes and 20% of configured stack, whichever is greater, at its high-water mark |

## Gate B — first vertical slice

The test is a single automated scenario: browser install, blank-device
provisioning, OSCQuery discovery, one-strip control, settings save/reboot, valid
OTA, deliberately invalid OTA, and rollback.

| ID | Measurement | Pass threshold |
| --- | --- | --- |
| `B-01` | End-to-end repetitions | 20 consecutive passes per reference target with no manual serial intervention after flashing starts |
| `B-02` | Settings interruption | for 1,000 randomized power cuts during save, boot yields exactly the previous or new valid generation, never a hybrid/default caused by corruption |
| `B-03` | Filesystem replacement interruption | for 1,000 randomized cuts, the named asset is the old or new verified file and unrelated files remain intact |
| `B-04` | OTA interruption | 25 cuts in each erase/write/verify/boot-confirm phase; every device returns to a bootable confirmed image without a programmer |
| `B-05` | Discovery/schema | OSCQuery legacy snapshot and V2 descriptor schema both match the live registry; no hand-authored UI control is required for the synthetic component |

The current row-by-row M3 audit is
[`2026-08-15-gate-b.json`](evidence/gate-b/2026-08-15-gate-b.json). A `partial`
record is deliberately not a Gate B pass; every threshold above remains
binding.

## Gate C — production LED engine

Each driver records its physical minimum frame period from pixel count and bus
timing. A deadline is never configured faster than that physical limit.

| ID | Measurement | Pass threshold |
| --- | --- | --- |
| `C-01` | Render-path allocation trace | zero heap allocations/frees after render startup in compositor, buffer submission, and driver completion paths |
| `C-02` | Forbidden-operation instrumentation | zero filesystem, log, network, or blocking component callback calls from render/output task context |
| `C-03` | Deadline run | zero missed physically-valid output deadlines in 3,600 s while Wi-Fi is saturated bidirectionally and settings/metrics are queried at 10 Hz |
| `C-04` | Queue behavior | overload produces the configured drop/coalesce result, exact overflow metric, bounded producer time, and no memory growth |
| `C-05` | Golden color vectors | byte-exact pass for channel order, 8/16-bit conversion, linear-light transform, correction, calibration, alpha, and power limiting |
| `C-06` | Heap stability | after a 1 h warm-up, minimum free heap falls no more than 4 KiB over the next 72 h and has no later 1 KiB downward step without a correlated bounded event |
| `C-07` | Soak health | 72 h per canonical target/profile with zero panic, WDT, unexpected reset, corrupt frame, stuck output, or unhandled queue overflow |

## Hardening and cutover gate

| ID | Measurement | Pass threshold |
| --- | --- | --- |
| `CUT-01` | Boundary fuzzing | settings, OSC, OSCQuery, file, ESP-NOW, and WASM targets complete their committed corpus plus 24 h per target with no sanitizer finding, panic, hang, or unbounded allocation |
| `CUT-02` | Reset/fault matrix | every brownout, reset, network loss, corrupt-storage, and OTA injection reaches a documented safe outcome and exposes a diagnostic reason |
| `CUT-03` | Profile matrix | minimal, standard, LED-heavy, sensor-heavy, and full canonical profiles build on every supported target; board-specific exclusions are explicit manifest constraints |
| `CUT-04` | Resource headroom | all tasks and internal heaps meet Gate A reserve under their worst documented workload; no canonical profile exceeds its partition or static memory budget |
| `CUT-05` | Compatibility | every preserved V1 fixture passes; every intentional difference has approval, migration notes, and a user-facing diagnostic |
| `CUT-06` | Release progression | alpha and beta artifacts have signed manifests, rollback instructions, known-issue lists, and field evidence before default-branch or V1-layout changes |

## Evidence ownership

Host tests can satisfy parser, schema, lifecycle, golden-vector, and generation
evidence. QEMU or simulator evidence is supplemental. Boot, timing, radio, power,
sleep, OTA interruption, and long soak thresholds require physical target boards.
No document-only change can mark those rows `pass`.
